## Entry e1
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: T.tile.topk / 「count 非 32 倍数时 Sort 的 pad 修补在 dav_c220 上不生效」
- **type**: known_bug_avoidance
- **severity**: high
- **status**: pending

**Observation**:
`T.tile.topk(dst, src, K, count)` 在 `count` **不是 32 的整数倍**时会读到未初始化 UB。
底层 `Sort32` 消费 `ceil(count/32)*32` 个元素，`tl::ascend::Sort()` 用一个 **masked `AscendC::Duplicate`**
去补 `padCount = alignedCount - actualCount` 个余数槽位——**该修补在 dav_c220 上不生效**，
于是这些槽位保留 UB 里的历史垃圾值，被当成真实候选参与排序。
后果不是崩溃，而是**静默产出错误结果**（本例中 `tau_out` 变成 `1e+30` 量级的垃圾，且降级守卫 `valid` 不触发，
错误沿链路传播到 `tok_out`）。

**Evidence**:
codegen 级证据（修复前后同一位置）：
```
PRE-FIX  ztt = ascend_ub.GetWithOffset<float>(313, 144640)          // 1252 B，非 32B 倍数
         TopK<float>(l_dst, ztt, tmp, 256, /*repeatTimes=*/10, /*actualCount=*/313)
FIXED    ztp = ascend_ub.GetWithOffset<float>(320, 144640)         // 新增，1280 B
         copy_gm_to_ub<float,320,1>(ztp, logits+4096, 30863, 1, 313, -CUDART_INF_F)  // 7 个槽位补 -inf
         TopK<float>(l_dst, ztt, tmp, 256, /*repeatTimes=*/10, /*actualCount=*/320)
```
对照 `tilelang/src/tl_templates/ascend/common.h:1663-1707`：`alignedCount = repeatTimes*32`；
`padCount = alignedCount - actualCount`。修复前 320−313 = **7 > 0** → 进 `in_block_offset != 0` 分支 →
`AscendC::Duplicate(src[312], negInf, masks, 1, 1, 0)`（dav_c220 上无效）；修复后 320−320 = **0** → 整个
`if (padCount > 0)` 块不可达。
决定性复现手法：**UB 投毒**（先用一个 `T.tile.fill(buf, 1e30)` 的 kernel 把每个 AIV 的 UB 填满已知字面量，
再 launch 被测 kernel）⟹ 修复前 8/8 实验臂全部失败且 `tau_out == 1.0000000150474662e+30`（= fp32(1e30)，
即投毒字面量原样读出），修复后 8/8 全过（**在持续投毒下仍全过**）。
文档侧佐证：`references/api-compute.md:715` 已写「src 的大小需要满足 32 或 32 的整数倍」——代码违反了它。
**但文档给出的示例写法本身也不安全**：buffer 320 + `actual_num=313` 且不预填充 ⟹ 实测 512/512 全错（即使不投毒）。

**Proposed change**:
① 在 `T.tile.topk` 的 API 文档里把「count 必须是 32 的整数倍」升级为**硬约束 + 显式警告**：不满足时
`Sort()` 的 masked `Duplicate` 补位在 dav_c220 上不生效，会读到未初始化 UB 并**静默产出错误结果（不报错、不崩溃）**。
② 给出唯一安全写法：把源缓冲扩到 `PAD = ceil(count/32)*32`，用 `T.copy(..., pad_value=-inf)`（或对应中性值）
从 GM 直接填充到 PAD 宽度，再 `topk(..., PAD)`，使 `padCount == 0`。**不要**依赖「buffer 开大 + actual_num 传小值」。
③ 修正 `api-compute.md:715` 附近的示例，使其符合 ② 的安全写法。

## Entry e2
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: UB→UB 拷贝 / 「非 32B 倍数的 count 被静默截断到 8 个 fp32 的倍数」
- **type**: known_bug_avoidance
- **severity**: high
- **status**: pending

**Observation**:
UB→UB 的 `T.copy`（底层 `copy_ub_to_ub` / `AscendC::DataCopy`）在 count 对应字节数**不是 32B 倍数**时，
会**静默截断到 8 个 fp32 的倍数**，丢掉尾部 `[count - count%8, count)` 区间的元素——**不报错、不告警**。
这是一个与 e1 独立的第二个缺陷，两者都被同一处 `TAIL_PAD` 修掉。

**Evidence**:
用「哨兵最大值」法定位（把某个尾索引置为全行最大，看它是否出现在 top-k 结果里），实测被丢弃的索引恰为
`(TAIL//8)*8 … TAIL-1`：
```
TAIL=313 → 丢弃 {312}        TAIL=261 → 丢弃 {256..260}
TAIL=511 → 丢弃 {504..510}   TAIL=257 → 丢弃 {256}
```
tail-adversary 扫描（对每个尾索引轮流放哨兵）在修复前 kernel 上 **3 次独立运行输出逐字节相同**，
`dropped = 1/1/7/5`，与上式完全吻合 ⟹ 确定性行为，与 UB 内容无关（这一点与 e1 不同）。
对齐对照组（`TAIL=0`、`TAIL=2048`）修复前即通过，符合理论。

**Proposed change**:
新增 troubleshooting 条目：症状「尾块/非对齐长度下 top-k 或排序结果少了最后几个元素，且不报任何错」→
成因「UB→UB copy 的 count 非 32B 倍数时被截断到 8 个 fp32 的倍数」→
解决「把拷贝长度对齐到 32B 倍数（`ceil(n/32)*32`）并用 `pad_value` 填充多余槽位，或直接改走 GM→UB 的
`T.copy(..., pad_value=...)`（该路径会正确处理非对齐 actual count）」。
并在 `T.copy` 的 UB→UB 小节加一句显式警告：**count 非 32B 倍数时行为是静默截断，不是报错**。

## Entry e3
- **target_skill**: tilelang-custom-skill/tilelang-error-fixer
- **target_artifact**: skill
- **target_section**: 诊断方法论 / 新增「间歇性缺陷的判别与确定性放大」
- **type**: unclear_workflow
- **severity**: high
- **status**: pending

**Observation**:
error-fixer 里没有针对「间歇性 / 时好时坏」缺陷的方法论，也没有「UB 投毒」这类**确定性放大**手法。
本周期正是靠投毒把一个 13% 概率触发的缺陷变成 100% 确定性失败，才使它可研究、可验收；
另一半定证靠的是 codegen 级结构证明（`GetWithOffset` 的 count/offset、`TopK` 的 `repeatTimes`/`actualCount`、
`padCount` 是否为 0、拷贝字节数是否 32B 对齐），这类证据不依赖任何运行，比统计重跑强得多。

**Evidence**:
同一 binary、同一输入，实测可在「300/300 全干净」与「60/60 全失败」之间翻转；
`stab_case5` 在 V2 run 0 失败、在 rerun 1–2 通过，而 `stab_B7_V4409_bv2048` 在 rerun 1 通过、rerun 2 失败。
投毒后 `tau_out` 恒等于投毒字面量 `1.0000000150474662e+30` ⟹ 直接证明是读未初始化 UB。
未投毒的独立探针（300 次 launch × 2 路径）在修复前 kernel 上**也全干净** ⟹ 统计重跑对该缺陷零检出力。
最终修复的验收不依赖任何自然复现，而是：codegen 结构证明 + 投毒放大 + tail-adversary 哨兵扫描（3 次运行逐字节一致）。

**Proposed change**:
在 error-fixer 的诊断流程里新增一节「间歇性缺陷」：
① 判别 —— 同 binary 同输入结果随**设备历史**变化 ⟹ 未初始化内存读（UB/L1/L0 残留），**不是**竞态；
此时「重跑 N 次都通过」在两个方向上都无证据力，禁止用它判定修复有效；
② 放大 —— 用投毒 kernel 把目标内存层级填满已知字面量（如 `1e30` / `0xdeadbeef`），把概率性缺陷变成确定性缺陷；
注意 UB 投毒会跨 launch 残留，**每个实验臂必须独立进程**；
③ 定证 —— 读生成的 AscendC 源码，核对 buffer 的 `GetWithOffset(count, offset)`、算子的 `repeatTimes/actualCount/padCount`、
拷贝字节数是否 32B 对齐；结构证明不依赖运行，是最强证据；
④ 验收 —— 修复后必须在**持续投毒下**仍全过。

## Entry e4
- **target_skill**: tilelang-op-test-design
- **target_artifact**: skill
- **target_section**: 分层测试套件 / `--level all` 的层级组成 + 非对齐尾块的强制覆盖
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
两个问题。（1）`--level all` **不包含 `stress` 层**（实测 `all = l0 + l1 + stability + l2 + boundary`）。
而 `stress`（UB 投毒）是 stale-UB 这一半根因的**唯一确定性检测器**；`all` 只通过 tail-adversary 无条件覆盖
「截断」那一半，对「读脏 UB」那一半只能靠 UB 恰好是脏的才偶然命中。⟹ 在刚开机的干净设备上，
修复前的 kernel 有可能通过 `--level all`。（2）测试设计没有把「尾块长度非 32 倍数」列为强制覆盖维度，
而这正是两个根因的共同触发条件。

**Evidence**:
`test_r4_fused_sampling.py --help` 的 levels = `{l0, l1, l2, boundary, stability, stress, all}`；
`stress` 需显式 `--level stress` 才跑（`--stress-reps` 默认 200）。
实测：修复前 kernel `--level stability` 3/3 次 exit 1、`--level stress --stress-reps 60` exit 1（5 FAIL，`tau_out max=1.000e+30`）；
而 stability 的 rerun 1–2 中 `stab_case5` 又通过 ⟹ 未投毒时检出力不稳定。
根因触发条件统计：全部 36 个评测用例中**只有 case 5（TAIL=313）满足 `TAIL%32 != 0`** ⟹ 覆盖极稀。
修复后新增 case 17（B=16, V=152377, TAIL=825, `TAIL%32=25`）作为大 shape 回归面。

**Proposed change**:
① 明确 `--level all` 的层级组成，并要求把 UB 投毒类稳定性检查**纳入默认 all**（或在 `stability` 层内内置一次投毒 pass），
理由是「未投毒的重复执行对未初始化内存缺陷检出力不稳定」。
② 在覆盖维度里新增一条强制项：**凡 kernel 存在尾块/remainder 分支，必须覆盖 `TAIL % 32 != 0` 且 `TAIL >= 最小处理粒度` 的用例**
（并说明这是 Ascend 32B/32 元素对齐约束的直接后果）。
③ 补一条判据：对含尾块分支的 kernel，单次通过不构成证据，需重复 N≥20 次且逐次 bit-identical。

## Entry e5
- **target_skill**: tilelang-op-design
- **target_artifact**: skill
- **target_section**: 技术约束检测 / 新增「32 元素·32 字节对齐」专项检查
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
op-design 的技术约束检测清单（三维 Kernel、threads、动态边界、L0C 容量、GEMM 非整除等）里
**没有「向量算子的 count / 拷贝长度必须是 32 元素（或 32 字节）的整数倍」这一项**，
也没有要求在设计阶段就为尾块给出对齐补齐方案。结果是对齐问题留到运行期才以「静默错误结果」的形式暴露。

**Evidence**:
R4 设计（`DESIGN.md` / `DESIGN_v01b.md`）对尾块只处理了「narrow-reduce 的 `real_shape`/`BufferRegion ≤ 256B」
与「`T.serial(0)` 空循环」两类约束，**未识别 `T.tile.topk` 与 UB→UB copy 的 32 对齐要求**；
`V % BV = 313` 的设计被判定合法（因为 `313 >= K_MAX`），实际却同时踩中 e1（`padCount=7`）与 e2（`313%8=1`）。
修复方案（`TAIL_PAD = ceil(TAIL/32)*32` + `pad_value=-inf` 的 GM→UB 填充 + `topk(..., TAIL_PAD)`）
本可以在设计阶段直接给出，代价仅 +1280 B UB（实测 UB 151364/196352 B，无需降 BV）。

**Proposed change**:
在技术约束检测清单中新增一项「**32 对齐约束**」：
凡设计中出现①按 `BV` 分块且 `V % BV` 可能非 0 的尾块、②`T.tile.topk` / 排序类原语、③UB→UB `T.copy`，
必须在设计文档里显式给出尾块的对齐补齐方案（补齐宽度、填充中性值、由谁填充），
并注明「count 非 32 倍数时 Ascend 侧是静默错误而非报错」。同时把该约束与既有的
「narrow-reduce ≤256B」「`T.serial(0)` 空循环」并列为尾块设计的三条必查项。

## Entry e6
- **target_skill**: cann-bench/bench_lab/op_skill
- **target_artifact**: skill
- **target_section**: 评测结果解读 / 「HAP 不可跨任务比较」与「cap 全绑定时基线测量失去量级意义」
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
两条会直接导致误读分数的机制，评测报告必须显式披露：
（1）**HAP 不可跨任务/跨算子比较**——同一份墙钟时间在不同任务上得分可以差数倍，因为 `t_hw` 分解里的
vector 操作计数是算子特有的。（2）当 **cap 对所有用例都绑定**时，`baseline_perf_us` 完全由 `t_hw` 决定
（= `10·t_hw`），辛苦实测的基线只提供「比 cap 慢多少倍」的下界证明，**不提供任何量级信息**，
此时分数的全部差异都来自 `t_hw` 建模，而不是来自与真实基线的对比。

**Evidence**:
（1）实测：case 15（B=64, V=152064）同一 shape 下 `t_hw` fused 78.31 µs vs mask 21.54 µs（3.6×，
源于 vector 计数 45.25 vs 10.25 op/elem），直接导致发布基线 783.10 vs 215.40 µs；
若某实现两路都跑 985 µs，则 fused 得 HAP 0.271、mask 只得 0.167。
（2）36/36 用例 `published == cap == max(10·t_hw, 10)`，clamp 因子 16.99×–336.81×（中位 55.91×）；
22/36 用例 `t_hw` 仍被 clip 在 1 µs 下限 ⟹ 其 cap 恒为 10 µs。
量级信息只能从「未封顶」口径读：geomean 加速比 fused 5.88×→**10.4×**、mask 8.22×→**16.5×**（18 用例，含生产 shape）；
生产 shape case 15 单点 fused **13.35×**、mask **51.49×**。
两口径总分：fused 56.47（capped）vs 93.24（raw）；mask 56.04 vs 95.32。

**Proposed change**:
在评测工作流文档里增加「结果解读必读」小节：
① 明确 **HAP/算子分不可跨任务比较**，跨算子对比只能用「对同一 `t_hw` 口径的达成率 `t_hw/elapsed`」或「对同一实测基线的加速比」；
② 报告 HAP 时**必须同时披露 cap 是否绑定、绑定比例、clamp 因子分布**，cap 全绑定时要同时给出未封顶口径的分数与加速比；
③ 提示 `t_hw` 被 clip 到 1 µs 下限的用例对 HAP 无判别力（此时 HAP ≈ `9/(T_cand+8)`，是 launch 开销的倒数代理），
应在用例矩阵设计阶段就用大 `B·V` 把 `t_hw` 顶出下限（R4 的经验值：fused 需 `B·V ≳ 1.3e5` 才刚过 1 µs）。
