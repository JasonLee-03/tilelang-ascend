  case7 fused `732.00 → 1360.25us = 慢 1.90×`

## Entry e2
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: `references/performance-antipatterns.md`（新增条目，与既有 11 节并列）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
反模式清单**完全没有「launch 数膨胀暴露框架级 host dispatch 成本」这一条**，也没有任何地方给出
**tilelang 在 Ascend 上的 per-launch host 成本量级**。缺少这个常数，就无法判断"多切一个 kernel"是否划算——
而这个常数大到足以推翻直觉：它比许多小 kernel 的**整个设备时长**还大 1~2 个数量级。

**Evidence**:
`perf_tuning/round3_host_overhead/attribution_report.md`（381 行，7 个探针，全部只读实测）：
- **per-launch host 成本阶梯**（probe3，4 个 case）：**L0 裸调 ~196–206us** → L3 +harness guards ~405–466us → L5 +msprof ~464–537us
- **加性分解**（Orchestrator 独立复算 `L0+C2+C1 = 500.17us` vs 报告 `499.638us`，OK）：
  C4 tilelang 框架 dispatch ≈**135–158us**（单一最大原语 `Analyzer()` = **122.603us** median，n=500，stdev 3.504；GC 关闭后仍 120.352 ⟹ 非 GC 抖动）
  + C5 ACL launch 残差 ≈17–38us = L0 200.5us；+ C2 harness guards **233.40us** = L3 433.9us；+ C1 msprof 插桩 **65.73us** = L5 499.6us
- ⭐ **不是算子特有，是框架级**（probe2 对照组）：`torch.add`(NPU) 仅 **17.905us**/launch；
  **一个空 tilelang kernel（零算子逻辑）= 160.6（0-alloc）/ 180.5（1-alloc）us**；R4 wrapper L0=200.5us 只比最小 tilelang kernel 高 ~20–40us
  ⟹ **≳90% 的裸发射成本是任意 tilelang kernel 都要付的**
- **我们自己的 host wrapper 只占 <2%**（probe5 `C_pct` = 0.97 / 1.60 / 0.98 / 1.97%）⟹ wrapper 瘦身不值得做
- **规模**：case13 fused 设备时间仅 23.84us，墙钟 416.75us ⟹ **94% 的墙钟是 host 开销**
- **缓解已量化**：ACL graph capture 把 per-launch host 降到 **2.8–6.6us（30–70×）**，端到端 `speedup_L0` **3.5–6.9×**

**Proposed change**:
新增反模式条目「**launch 数膨胀暴露框架级 host dispatch 成本**」：
识别特征 = 优化增加了 kernel 个数 / launch 次数，且单个 kernel 的设备时长与 per-launch host 成本同量级或更小；
给出实测常数表（L0 ≈200us、+harness guards ≈434us、+msprof ≈500us，`Analyzer()` 独占 ~123us）
与**空 kernel 对照组方法**（用一个零逻辑 tilelang kernel 测 per-launch 底线，以区分"框架级"与"算子特有"）；
替代方向 = ① 优先减少 launch 数而非增加；② 若必须增加，先测 per-launch host 成本再决定；
③ 部署侧用 **ACL graph capture + D2D copy-in**（唯一能消除根因的手段，30–70×，已证 bitwise，不改 kernel；
代价：graph 会烘焙设备地址 ⟹ 输入轮换必须走 copy-in 80–89us/step、每 shape 各需一次 capture、一次性 capture 3.5–5.5ms）；
④ 明确指出**合并 kernel 以减少 launch 在 Developer 模式下通常不可行**（无 grid barrier，见 e8）。

**Observation**:
Step 1 只要求采一次基线，**没有要求标定测量噪声底、也没有要求设置同码对照臂**。
后果是：一个固定的百分比采纳门槛（本项目用 3%）在**绝对时长很小的 case 上等于甚至低于逐 case 噪声**，
于是会随机产生假阳性/假阴性。本周期就因此出现一次"单样本判定 DO NOT ADOPT、需要额外仲裁"的事件。

**Evidence**:
item A 的单样本 A/B 把 **case13 mask 标为 +4.24%**（14.620→15.240us，绝对仅 **+0.62us**），
`cmp_itemA.py` 据此如实输出 `criterion2=FAIL / DO NOT ADOPT`（该原始记录被刻意保留为 `cmp_itemA_single_sample_1run.log`）。
仲裁数据：**同码漂移对照组（base2 vs base1，代码逐字节相同）自身最大移动 2.385%**；
池化 5 base + 4 cand 的 harness 重复采样 → 中位 14.70 vs 14.88 = **+1.224%**，两分布重叠；
交错空探针（kernel sha 前后未变）的**纯噪声包络达 5.18%**，其中更小的 case1 mask（11.14us）纯噪声即 **−5.03%**，量级已超过被标记值。
⟹ **3% 门槛在 ~15us 量级的 case 上低于 harness 逐 case 噪声底**。
最终由 Orchestrator 用**结构性**论证定案（比统计仲裁更强）：`_r4_split_plan(6,2304,128,2048)` 在 guard=8.0 与 1.540 下
**都返回 `(False,2,1,1)`** ⟹ case13 两臂走同一路径、生成码逐字节相同 ⟹ 任何 delta **定义上是噪声**。
另一处同类现象：round 2 #4 中，**生成码逐字节相同、JIT 缓存键都没变**的对照组移动了 +0.531%，

**Proposed change**:
Step 1 增加「噪声底标定」子步骤：① 基线采集必须包含一个**同码对照臂**（同一份代码测两次），
其逐 case 最大移动即为本会话噪声底；② 采纳门槛必须与噪声底比较——
**若门槛 ≤ 噪声底，该 case 的判定无效**，必须改用重复采样取中位 + 分布重叠判据，或改用结构性论证
（证明该 case 的生成码/分派未变 ⟹ delta 定义上为噪声）；③ 对绝对时长 < ~50us 的 case，
明确禁止用单样本百分比下结论；④ 原始判定记录（即使后来被仲裁推翻）**必须保留**，不得覆盖。

## Entry e4
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: skill
- **target_section**: `references/api-kernel-memory.md`（buffer rank 语义）+ `references/api-compute.md` §4.12 `T.tile.topk`（L695-716）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
`T.tile.topk` 的 `actual_num` **不是**调用方传的 count，而是由源 buffer 的 shape 推导：
`max_actual_num = Σ src.shape`（**求和，不是求积**）。因此把 rank-2 `[1, BV]` 当作 rank-1 `[BV]` 的等价写法传进去，
会得到 `1 + BV`（4097 而非 4096）→ `repeatTimes = ceil(4097/32) = 129` → 覆盖 `129*32 = 4128 > 4096` 个槽位
⟹ **静默读越界 32 个元素**。没有报错、没有告警。文档完全没提这一点，也没提"topk 源必须是 rank-1"。

**Evidence**:
源码逐行核实（Stage 1 rev3 与 Stage 2 各自独立复核）：`tilelang/language/ascend_tile.py:635-647` ——
`max_actual_num = 0` → `for dim in src.shape: … max_actual_num += dim_simplified.value` → `repeatTimes = (max_actual_num + 31) // 32`。**确为求和**。
发现现场：round 2 #4 把 K1 的 `z_ub` 从 rank-2 `[1,BV]` 改成 rank-1 `[BV]` 以便直接充当 topk 源，
交付代码注释记录了该陷阱（`r4_fused_sampling.py` 主块路径）。
现有文档 `api-compute.md` §4.12「注意事项」**只有一条**："`src` 的大小需要满足32或32的整数倍"，
既无 rank 约束、无 `actual_num` 推导规则、也无越界后果。
（与上一份 journal `-20261010-095041` 的 e7 是**同一 API 的不同缺陷**：e7 讲代价模型（无 partial-select、
`topk(K=1,N)` 做完整 Sort）与 32 倍数违规的静默数值错误；本条讲 **rank 语义导致的静默越界读**。）

**Proposed change**:
在 `api-compute.md` §4.12「注意事项」增补：
① **`actual_num` 由 `Σ src.shape` 推导（求和非求积）**，因此 **topk 的源 buffer 必须是 rank-1 `[N]`**；
传 rank-2 `[1,N]` 会得到 `N+1` → `repeatTimes` 多 1 → **静默读越界最多 32 个元素**，无报错；
② 给出 rank-1 与 rank-2 的对照示例并标明哪个是错的；
③ 在 `api-kernel-memory.md` 的 buffer rank 说明处交叉引用：**`[1,N]` 与 `[N]` 对 `T.copy`/`T.tile.*` 的多数
二元/一元运算是可互换的（`ascend_tile.py:1030-1086 / :1229-1252` 只比较 `math.prod(extent)`，rank-agnostic），
但对 `topk`（求和）与 `reduce_*`（见 e5）不可互换**——这个"部分 rank-agnostic"的边界必须写清。

## Entry e6
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: `T.alloc_shared` 与其 use 必须处于同一词法 `if` 作用域
- **type**: runtime_error_recipe
- **severity**: high
- **status**: pending

**Observation**:
在 `if <cond>:` 内 `T.alloc_shared(...)`、却在其**后面**（同函数但不同 `if` 块）的循环里使用该 buffer，
会在编译期报 `error: Undefined variable: <name>`。报错信息只说"变量未定义"，
完全看不出根因是 **TIR 的词法作用域**，也看不出修法是"把 use 移进同一个 `if`"或"把 alloc 提到 `if` 外"。
这在需要按条件分配 buffer（例如尾块专用缓冲、split 路径专用缓冲）时极易踩到。

**Evidence**:
Stage 1 rev3 的编译实证记录（`DESIGN.md` §13.6，已固化为设计约束 **N6 / E-S1**）：
探针 `/tmp/opencode/refine.py` 的 K1A 单循环变体失败 —— `error: Undefined variable: z_ub`
（`alloc` 在 `if n_blk_full > 0:` 内、`use` 在其后的 `for` 里）；
修补后又报 `error: Undefined variable: ztp`（同一原因）。
正确形态见 `refine3.py` 的 v3 变体（把尾块 hoist 到 `if TAIL > 0:` 内 + `if sid == S_TAIL:`），**编译成功**。
相关既有知识：交付 kernel `r4_fused_sampling.py:188-190` 的注释记录了**另一面**——
无条件 `alloc_shared` 会留下 dead buffer，而 dead buffer 没有预分配地址 ⟹ codegen 失败
（`Cannot find pre-allocated address for buffer`，`codegen_ascend.cc:828`）。
⟹ 两条合起来才完整：**既不能无条件分配（dead buffer → codegen 失败），也不能跨 `if` 作用域使用（Undefined variable）**。

**Proposed change**:

## Entry e11
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: `references/optimization-guide.md` §2.1「Split-K 切分策略（Cube 核）」（L63-91）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
§2.1 的切分策略**只针对 Cube 核**，且**完全没有「波量化（wave quantization）」这条决定成败的算术**。
缺失的判据是：切分**只在 `block 数 < 物理核数` 时有收益**；一旦 `切分后 block 数 ≥ 核数`，
"多波 × 每波少量工作"与"少波 × 每波全量工作"的**总工作量完全相同**，切分只多付一次 launch ⟹ **严格变慢**。
没有这条，设计者会把切分边界设在错误的位置（本项目 Orchestrator 就设错了，被 Stage 1 用定理纠正）。
另外**纯 Vector 算子的切分**（沿归约/扫描轴 split + 跨 split 归约）在指南里没有任何对应章节。

**Evidence**:
Orchestrator 给出的初始判据是"`b_num < 20` 走 split、`b_num >= 20` 走现行"（20 = `cube_core_num`）。
Stage 1 rev3 §5.8.3 **定理 P2** 证明该边界错误：`b_num ∈ [11,19]` 时 `S=2` 会把 grid 推到 `2*b_num ∈ [22,38] > 20` ⟹ **2 波**，
而"2 波 × 半量块"与"1 波 × 全量块"的 Sort 工作量**完全相同**，只多一次 launch ⟹ 严格变慢。
正确判据是 `S_cap = CUBE_CORE_NUM // b_num`，`S_cap < 2` 即不切 ⟹ 边界应收紧到 **`b_num > 10`**。
Orchestrator 已批准该收紧；实测印证：case15（`b_num=32`）若 `S=2` → `blocks=64` → `waves=ceil(64/20)=4` × `scan(V/2)=228us` = **912us**，
与现状 **911.6us 完全相同**（零收益）。
波数定律本身也已实测标定并验证：`K1_us ≈ ceil(ceil(B/2)/20) × scan(V)`，
两组独立数据点 —— 同 `V=152064`：case7(`b_num=2`,1 波) 451.3us vs case15(`b_num=32`,2 波) 911.6us，比值 **2.02** 对波比 **2.00**；
同 `V=32768`：case12(1 波) 120.3us vs case16(4 波) 532.9us，**4.43** 对 **4.00**；
每波单位成本近似恒定（`V≈152064` 时 case 7/15/17 = 451.3 / 455.8 / 455.9us，极差 0.9%）。
运行时亦已验证：msprof 读出的 `Block Num` 在 **864/864 step** 上与计划一致、定理 P2 零违反，
case7 fused = `[20,2,20,2]`，最紧点 split-并行 `Block Num = 20 == CUBE_CORE_NUM`（恰 1 满波）。

**Proposed change**:
① 把 §2.1 标题与内容从「Split-K 切分策略（Cube 核）」扩为**通用切分策略**，新增 Vector 核沿扫描/归约轴切分的形态
（附"跨 block 归约只能靠多 kernel 顺序 + GM workspace"的交叉引用，见 e8）；
② 增加**波量化判据**（必须给出算式）：`waves = ceil(block_num / core_num)`；
切分后 `block_num' = block_num × S`；**当且仅当 `ceil(block_num/core_num) > ceil(block_num×S/core_num) / S` 时有收益**，
否则总工作量不变而多付 launch ⟹ 严格变慢。给出推荐形式 `S_cap = core_num // block_num`（`S_cap < 2` 即不切）；
③ 增加**强制的运行时验证步骤**：从 msprof 读 `Block Num` 与计划值逐 step 比对，并断言每个并行 kernel 的
`Block Num ≤ core_num`（即切分后仍是单波），把它作为切分类优化的验收门禁；
④ 提醒切分类优化必须与 e1/e2 联查：**切分会增加 launch 数**，设备时间的收益可能被 host dispatch 成本吃掉。
