# Skill Feedback - r4_fused_sampling (msprof 流水采集)

> 本次会话不是算子开发流程（未跑 Stage 1/2/3），而是用户直接要求的 msprof 数据采集任务：
> 为 MindStudio Insight 采集 R4 的 op 模式性能数据与 simulator 模式指令流水。
> 以下 entry 全部来自这次实测（Ascend910_9362 / CANN 9.2.0 / tilelang 0.1.4+d75300e wheel），
> 落盘工件见 `examples/R4/prof/`（README.md §1-§6 + prof_r4_pipeline.py + collect_pipeline.sh）。

## Entry e1
- **target_skill**: tilelang-custom-skill/tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: 执行步骤 → Step 1: 基线采集
- **type**: missing_workflow
- **severity**: high
- **status**: pending

**Observation**:
SKILL.md 的性能采集只写了 `msprof op`（真实硬件），完全没有 `msprof op simulator`（指令流水仿真）
这条链路，而"采集流水图给 MindStudio 看"是算子调优里独立且高频的需求。缺的具体信息有四项，
本次全部靠现场摸索补齐：① `--soc-version` 的合法取值必须来自
`$ASCEND_HOME_PATH/tools/simulator/` 下的**目录名**（本机 910b2 要用新命名 `Ascend910_9362`，
`Ascend910B2` 也在列表里；文档示例里的 `Ascend910B4` 是别的型号，照抄会直接失败）；
② `--launch-count` 的语义是"采集前 N 次 kernel 发射"，多 kernel 算子必须按一次调用实际发射数设置，
否则只采到第一个 kernel；③ 产物结构（`OPPROF_*/main_kernel/<launch>/simulator/{trace.json,
visualize_data.bin,core*.*/}`）与两种查看入口（`chrome://tracing` 加载 trace.json、
MindStudio Insight 加载 visualize_data.bin）；④ 仿真耗时随**每核工作量**增长，需要给出量级预期，
否则容易拿生产 shape 直接跑仿真然后干等。

**Evidence**:
- `grep -n "simulator|流水图|MindStudio|soc-version|launch-count" .agents/skills/tilelang-perf-optimization/SKILL.md`
  → 0 命中；该文件只有 `msprof op --kernel-name="main_kernel" ...` 一条命令。
- `msprof op simulator --soc-version=INVALID_SOC ...` → `[ERROR] --soc-version is invalid, please specify a simulator in $ASCEND_HOME_PATH/tools/simulator`；
  `ls $ASCEND_HOME_PATH/tools/simulator/` 实测含 `Ascend910_9362`、`Ascend910B2`、`dav_2201` 等 70+ 条目。
- 实测量级：case B=1/V=4096（每核 4096 元素、2 次发射）`Model RUN TIME: 43780.5 ms`；
  case B=8/V=16384（每核 32768 元素、3 次发射、16+4+4 核）`Model RUN TIME: 104536 ms`。
- 成功产物：`examples/R4/prof/output/sim_case3_mask_Ascend910_9362_20261014_164928/OPPROF_*/device0/main_kernel/{0,1,2}/simulator/trace.json`
  （54 MiB / 244,928 事件、27 MiB / 124,000 事件、1.7 MiB / 8,448 事件，均已 `json.load` 校验为合法 Chrome Trace Event Format）。

**Proposed change**:
在 Step 1 之后新增 "Step 1b: 流水（simulator）采集"，给出：命令模板
`msprof op simulator --soc-version=<$ASCEND_HOME_PATH/tools/simulator 下的目录名> --kernel-name="main_kernel" --launch-count=<一次调用的 kernel 发射数> --output=<dir> python3 <script>.py`；
`--soc-version` 的查表方法与报错样例；产物目录树 + `chrome://tracing` / MindStudio Insight 两种查看方式；
"仿真耗时随每核工作量增长，优先用小 shape 采流水、用生产 shape 采 op 模式"的选型建议 + 上述两个实测耗时锚点。

## Entry e2
- **target_skill**: tilelang-custom-skill/tilelang-perf-optimization
- **target_artifact**: troubleshooting
- **target_section**: 新建条目：simulator 采集后"算子代码热点图"为空
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
simulator 采集能拿到完整的指令流水（trace.json + 逐指令 `*_instr_exe_*.csv`），
但**算子代码热点图不可用**：每个核的 `*_code_exe_*.csv` 只有表头一行，因为 TileLang 编译出的
kernel 缺 `debug_line` 信息，工具无法把 PC 映射回源码行。这一点在采集前没有任何提示，
用户拿到产物打开 MindStudio 才会发现代码热点页是空的。

**Evidence**:
工具告警原文（`examples/R4/prof/logs/sim_case2_mask.log`）：
`[WARN] Failed to parse pc to code, maybe kernel missed debug_line information. If you need code call stack, please recompile kernel with -g option`，
随后 `[WARN] Code call stack is empty` / `[WARN] Lack of code info of files`。
落盘验证：`.../main_kernel/0/simulator/core0.veccore0/core0.veccore0_code_exe_20261014163638923.csv`
内容仅 `code,call_count,cycles,running_time(us)`（40 B）；同目录 `*_instr_exe_*.csv` 为 133,266 B 且有完整数据。
`docs/TileLang-Ascend Programming Guide.md` §6.2.2 只笼统写"编译选项（如添加 -g 省工程调试信息）"，
未说明不加的后果与 TileLang 侧该怎么加。

**Proposed change**:
新增三段式条目：症状 = simulator 产物里 `*_code_exe_*.csv` 只有表头 / MindStudio 算子代码热点图空白 +
上述 WARN；原因 = kernel 未带 `-g`，无 debug_line，PC→源码映射失败（指令流水不受影响）；
解决 = 需要代码热点时让 TileLang 侧带 `-g` 重新编译 kernel 后再采，只需流水图则可忽略该 WARN。

## Entry e3
- **target_skill**: tilelang-custom-skill/tilelang-perf-optimization
- **target_artifact**: troubleshooting
- **target_section**: 新建条目：msprof 解析阶段静默产出空/全零 CSV
- **type**: environment_pitfall
- **severity**: high
- **status**: pending

**Observation**:
msprof 的解析阶段（`msprof_analysis`，把原始 `PROF_*/DeviceProf*.bin` 转成
`kernel_details.csv` 等报表）链接的是**无版本号**的 `libsqlite3.so`。在只有 `libsqlite3.so.0`
进入动态链接器缓存的机器上，解析任务会整体失败，而采集阶段仍然报成功 —— 表现为 CSV 缺失或
`elapsed_us` 全零，极易被误读成"kernel 真的不耗时"。这条坑目前只记录在 R4 自己的脚本注释里，
perf skill 完全没提，属于会被反复重踩的环境级陷阱。

**Evidence**:
- 本次会话**未复现**该错误（因为按已记录配方预先规避），证据来自仓内既有记录：
  `examples/R4/bench/measure_baseline.py` 文件头注释 —— "CANN's profiler analysis stage (`msprof_analysis` …)
  links against the *unversioned* libsqlite3.so, which on this box only exists in /usr/local/sqlite3/lib …
  Without it every parse task fails (`Task [CANNTimelineParser] run failed.` + `ImportError: libsqlite3.so`)
  and no CSV is produced."
- `examples/R4/perf_tuning/perf_log.md:351` —— "`LD_LIBRARY_PATH` 以 `/usr/local/sqlite3/lib` 为前缀 ⟹
  全部 `elapsed_us` 非零，即该坑未踩"。
- 规避手段已固化进本次交付的 `examples/R4/prof/collect_pipeline.sh`（`export LD_LIBRARY_PATH="/usr/local/sqlite3/lib:${LD_LIBRARY_PATH:-}"`），
  两次 op 采集与两次 sim 采集的 CSV/trace 均正常产出。

**Proposed change**:
新增三段式条目：症状 = 采集日志显示成功但 CSV 缺失 / `elapsed_us` 全零 / `Task [CANNTimelineParser] run failed` +
`ImportError: libsqlite3.so`；原因 = `msprof_analysis` 需要无版本号 `libsqlite3.so`；
解决 = 采集前 `export LD_LIBRARY_PATH=<含 libsqlite3.so 的目录>:$LD_LIBRARY_PATH` 并重跑解析。
同时在 SKILL.md Step 1 的命令模板旁加一句环境前置提醒。

## Entry e4
- **target_skill**: tilelang-custom-skill/tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: 执行步骤 → Step 1: 基线采集（--kernel-name 说明）
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
SKILL.md 把 `--kernel-name="main_kernel"` 当成一个固定写法给出，但没有说明它的后果：
TileLang 的 `@tilelang.jit` kernel 内层函数惯例都叫 `main`，编译后**设备符号统一是 `main_kernel`**。
对单 kernel 算子无影响；对**一次调用发射多个 kernel** 的算子（融合链、split 路径），
`msprof op` 的报表按 op name 聚合，`OpBasicInfo.csv` 只有一行汇总，无法分离各 kernel 的时长 ——
而"哪个 kernel 是瓶颈"恰恰是调优的第一个问题。

**Evidence**:
- R4 的 host wrapper 一次调用发射 2~4 个 kernel：`examples/R4/r4_fused_sampling.py` 中
  `r4_topk_stats` / `r4_mask_sample` / `r4_gumbel_sample` / `r4_topk_stats_splitA|splitB` /
  `r4_gumbel_sample_splitA|splitB`，每个的内层函数都叫 `main`（`with T.Kernel(...) as (cid, vid)`）。
- 实测 `examples/R4/prof/output/op_case15_mask_20261014_163447/OPPROF_*/OpBasicInfo.csv` 只有
  2 行（表头 + 1 行）：`main_kernel,mix,853.880005,32,64,0,...` —— 8 次调用共 16 次发射被聚合成一行。
- 对照 cann-bench 口径可按 step 拿到逐 kernel 时长：`examples/R4/bench/reports/cann_performance_eval_20261012_201818.json`
  里 `"op_times": {"device_kernels": {"main_kernel": 26.0}}`（同样受限于同名聚合）。

**Proposed change**:
在 Step 1 命令模板下补一条约束说明：`main_kernel` 是 TileLang 全部 kernel 的统一设备符号；
多 kernel 算子用 `msprof op` 只能拿到聚合时长，要分离单 kernel 需（a）构造只发射目标 kernel 的
最小 workload 脚本，或（b）走 `kernel_details.csv` 的 per-step 口径，或（c）用 simulator 模式按
`--launch-count` 逐 launch 落盘（产物天然按 launch 编号分目录）。

## Entry e5
- **target_skill**: tilelang-custom-skill/tilelang-perf-optimization
- **target_artifact**: troubleshooting
- **target_section**: 新建条目：长仿真被外层 shell 超时打断后的数据恢复
- **type**: missing_workflow
- **severity**: medium
- **status**: pending

**Observation**:
simulator 采集是分钟级到小时级的长任务。若把它挂在会被超时杀掉的前台 shell（或普通
`nohup ... &` 但 stdout 仍连着该 shell）上，仿真跑完后**解析阶段会被 `Broken pipe` 打断**，
末尾还会打出 `[ERROR] Get Init data failed`，看起来像整次采集失败。实际上 dump 与解析产物往往已经完整落盘，
且 msprof 提供 `--export <DIR>` 可以只重跑解析，不必重跑仿真（仿真才是最贵的那一段）。

**Evidence**:
- `examples/R4/prof/logs/sim_case3_mask.log` 末尾：`Model RUN TIME: 104536 ms` → `[INFO] Model stopped successfully.`
  → `[INFO] Profiling running finished. All task success.` → 随后
  `[2026-10-14 08:53:39] [3170060] [ProfConfig.cpp:210] [ERROR] Get Init data failed` + `uname: write error: Broken pipe`
  （外层 shell 120 s 超时被终止所致）。
- 产物核验：`.../device0/main_kernel/{0,1,2}/simulator/` 三个 launch 的 `trace.json` +
  `visualize_data.bin` + 78 份单核 `trace.json`/`*_instr_exe_*.csv` **全部存在且合法**
  （`json.load` 通过，事件数 244,928 / 124,000 / 8,448），即数据可直接使用，无需重跑。
- `msprof op simulator --help` 明确提供恢复入口：`--export <DIR>  Simulator data directory to parse.`

**Proposed change**:
新增三段式条目：症状 = 长仿真末尾出现 `Broken pipe` / `Get Init data failed`，疑似采集失败；
原因 = 外层 shell 超时终止导致 msprof 收尾/解析进程被杀，而模型运行与 dump 已完成；
解决 = ① 先核验 `<output>/OPPROF_*/(device0/)main_kernel/<launch>/simulator/trace.json` 是否已存在且可解析，
② 需要补解析时用 `msprof op simulator --export <simulator 数据目录> --output <dir>`，
③ 预防：长任务用 `setsid nohup ... > log 2>&1 < /dev/null &` 完全脱离终端，或给足前台超时。
