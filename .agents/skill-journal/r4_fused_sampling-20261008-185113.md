## Entry e1
- **target_skill**: tilelang-custom-skill/tilelang-env-check
- **target_artifact**: skill
- **target_section**: 环境检查项清单 / 新增「CANN Profiler 导出链路可用性」检查项
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
env-check 只验证「kernel 能跑通」（quick_verify.py），不验证 **CANN Profiler 的导出链路能否真的产出
`kernel_details.csv`**。本机 `libsqlite3.so`（无版本后缀）只存在于 `/usr/local/sqlite3/lib`，而 ld cache 里只有
`libsqlite3.so.0`；CANN 的 `msprof_analysis` 阶段 dlopen 的是无后缀名 ⟹ 分析任务全部失败 ⟹
**不产出 `kernel_details.csv`** ⟹ 评测框架读到的 `elapsed_us` 全为 0。

**Evidence**:
`msprof_analysis` 报 `ImportError: libsqlite3.so`，伴随 `Task [CANNTimelineParser] run failed.` 等 9 条任务失败；
首次 baseline 采集 28/28 用例 `elapsed_us=0`。修法：`export LD_LIBRARY_PATH=/usr/local/sqlite3/lib:$LD_LIBRARY_PATH`
（无需安装任何东西）。加上后 6/6 profiler session 均产出非空 `kernel_details.csv`。
实证：`ldconfig -p | grep sqlite3` 只有 `/lib/aarch64-linux-gnu/libsqlite3.so.0`；
`find / -name libsqlite3.so` 只命中 `/usr/local/sqlite3/lib/libsqlite3.so`。

**Proposed change**:
在 env-check 的检查项中新增一条「Profiler 导出链路」：跑一次最小 kernel 的 `torch_npu.profiler`（Level1 + ExportType.Text），
断言 `kernel_details.csv` 存在且非空；失败时给出 `libsqlite3.so` 缺失这一具体成因与
`LD_LIBRARY_PATH` 前置修法。理由：这类失败**不报错、不崩溃，只把所有性能数据静默变成 0**，
是最难自查的一类环境缺陷，而任何性能调优 / benchmark 工作都以它为前提。

## Entry e2
- **target_skill**: tilelang-op-test-design
- **target_artifact**: skill
- **target_section**: L1 功能测试设计 / 新增「间歇性缺陷：每配置重复 N 次」门槛
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
测试设计对每个 L1/L2/Boundary 配置**只跑一次**。这让一个**每次 launch 约 13% 概率触发**的 kernel 缺陷
完整地通过了 Stage 2 的「62 [PRECISION_PASS] / 0 [PRECISION_FAIL]」门禁，直到 cann-bench 评测
（同一 wheel 反复跑 15 次）才暴露。单次通过的判定对「间歇性 / 非确定性」缺陷**零检出能力**。

**Evidence**:
cann-bench 评测中 `r4_fused_sampling` case 5（B=7, V=4409, K_MAX=256, BV=4096，尾块 `V%BV=313`）
15 次 harness 执行失败 2 次（13%）。失败形态：`tau_out` 个别行返回垃圾大有限浮点
（`2.7231e+19`、`6.6395e+24`、`6.4679e+32`、`4.4785e+37`），而 logits 值域仅 `[-10,10]`
（不变式 `tau <= row max` 被破坏）；`valid` 仍为 1 ⟹ 守卫不触发 ⟹ 垃圾阈值下游传播，
`tok_out` 退化为 0。同一次执行内 case 5 **stage 2 通过、stage 3 失败**（同输入、同 wheel）。
独立复现 15 次连续 launch 呈**严格周期 5** 的 bit-identical 垃圾值循环
（bad rows `[1,3,5] → [3] → [] → [] → [2,5] → 重复`）⟹ 指向输出缓冲轮转 / 读到 stale UB，而非随机噪声。
交付的 `test_r4_fused_sampling.py::l1_prime_V_B`（line 441）**确实覆盖** B=7/V=4409，但每配置只跑一次。

**Proposed change**:
在测试设计中为高风险形态增加「重复执行」门槛：对（a）尾块非 32B 对齐（如 `V%BV` 为质数）、
（b）kernel 内含 1 元素标量 UB 缓冲 / 跨块归并 epilogue、（c）多 kernel 串联 的用例，
每配置重复 N 次（建议 N≥20）并要求**逐次 bit-identical**，任一次不一致即判 FAIL。
同时把「同一配置 stage 间结果不一致」列为显式的非确定性告警。

## Entry e3
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: UB 标量缓冲 / 「1 元素 UB 缓冲的静默 stale 读」
- **type**: known_bug_avoidance
- **severity**: high
- **status**: pending

> ⚠️ **已被后续周期实证否定，请勿按本条 apply。**
> 本条写的怀疑面（`tau_k`/`tau_p`/`tau` 的 1 元素标量 UB 归并链）在 V01-b rev2 周期被证伪：
> `gather_mask`/`topk` 原语在 UB 投毒下 0 错误；奇数 B 越界行守卫假设同样被否定。
> 真正的两个根因是 ① `T.tile.topk` 在 `count` 非 32 倍数时 `Sort()` 的 masked `Duplicate` 补位在
> dav_c220 上不生效 → 读未初始化 UB；② UB→UB `T.copy` 在 count 非 32B 倍数时**静默截断**到
> 8 个 fp32 的倍数。二者详见 `r4_fused_sampling-20261009-113013.md` 的 **e1 / e2**（含 codegen 证据与复现手法）。
> 本条唯一仍然成立的部分是方法论层面：「1 元素 / 非对齐 UB 缓冲可能静默返回 stale 值而不报错」——
> 该教训已并入 rev2 的 e1/e2/e3，本条保留仅为频次追溯。

**Observation**:
现有已知问题只记录了「1 元素 UB→UB `T.copy` 会崩（<32B DMA 对齐，aicore 507015）」这一**显式崩溃**形态。
实测还存在更危险的**静默形态**：1 元素标量 UB 缓冲在 reduce / 跨块归并 epilogue 中被读到时，
可能返回**上一轮遗留的垃圾值而不报任何错**，且呈周期性复现（缓冲轮转）。
「不崩」不等于「读到了正确值」——这条必须写进 troubleshooting，否则后续算子会继续用 1 元素标量缓冲做归并。

**Evidence**:
R4 K1 `r4_topk_stats` epilogue（`r4_fused_sampling.py:213-263`）用 1 元素 UB 缓冲承载
`tau_k` / `tau_p` / `tau` 的 `T.tile.max` 链；case 5 间歇性产出 `tau_out = 2.7231e+19 / 4.4785e+37`
等垃圾值，`valid` 不触发、`m_out`/`s_out` 始终正确 ⟹ 缺陷局限在该标量归并链。
独立复现严格周期 5、bit-identical ⟹ 缓冲轮转读 stale，而非数值误差。
注：**根因未经确认**（对齐压力探针 8 配置 ×200 launch、含 600 次 case-5 原配置，0 违规——但探针运行在缺陷静默期，
无判别力）。本条记录的是「症状 → 怀疑面 → 规避方向」，不是已证实的因果。

**Proposed change**:
新增 troubleshooting 条目：症状「标量输出间歇性变成垃圾大数 / 周期性复现 / 守卫不触发」→
怀疑面「1 元素（<32B）UB 标量缓冲在归并 epilogue 中被 stale 读」→
规避「把参与归并的标量缓冲加宽到 ≥32B（如 `[8]`/`[1,8]`），或在归并前显式初始化目标缓冲」。
并把现有「1 元素 UB→UB copy 崩」条目扩写为「1 元素 UB 缓冲有两类故障：显式崩溃（507015）与静默 stale 读」。

## Entry e5
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: 性能评测基准设计 / 新增「HAP 锚点有效性」前置检查
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
perf-optimization 讲怎么优化，但不讲**怎么判断一个 benchmark 分数有没有意义**。cann-bench 的 HAP 有两个
会让分数失去判别力的机制，必须在选 shape 之前就算清楚，否则会得到一个「看起来是分数、实际是噪声」的结果。

**Evidence**:
① **`t_hw_us = max(raw, 1.0)` 的 1µs 下限会让小 shape 饱和**：R4 的 28 个用例中 **22 个** `t_hw` 被 clip 到 1.0µs
（fused 10/14、mask 12/14）。此时 `cap = max(10·t_hw,10) = 10µs`，HAP 退化成 `9/(T_cand+8)`
——测的是「比 1µs 慢多少倍」（近似 launch 开销的倒数），**不是「离硬件下界多远」**。
只有 `B·V` 足够大才有判别力：fused 约 45.25 op/elem ÷ 6.0e12 ⟹ `B·V ≳ 1.3e5` 才刚过 1µs 下限，
`B·V = 6.1e5`（B=4,V=152064）才到 4.89µs。**生产 shape B=64,V=152064（9.7e6 元素）反而不在矩阵里**。
② **`baseline_cap` 会整体抹平实测基线**：官方约定 `published = min(实测, max(10·t_hw,10))`
（`docs/hap_thw_model/README.md`，且 `tasks/metadata/910b2.json` 1060 条中 525 条正好等于 cap、ratio 中位数恰为 10.0000）。
R4 的未融合 torch 基线比 cap 慢 **17×–337×** ⟹ **28/28 全部被截断** ⟹ 同一个算子
「按 cap 基线」得 55.00/55.80 分、「按实测基线」得 92.51/94.43 分（geomean speedup 0.11×/0.13× vs 5.88×/8.22×）。
分数差异**完全来自 metadata 约定，与 kernel 无关**。

**Proposed change**:
新增一节「HAP/benchmark 锚点有效性前置检查」：选定 shape 矩阵前先算 `t_hw`，
要求**多数用例的 `t_hw` 明显高于 1µs 下限**（否则该用例对 HAP 无判别力，应加大 `B·V` 或明确标注为 launch-overhead 用例）；
并强制**同时报告 capped 与 uncapped 两套 HAP/speedup**，注明差异来自基线约定而非实现。

## Entry e6
- **target_skill**: cann-bench/bench_lab/op_skill
- **target_artifact**: troubleshooting
- **target_section**: 「评测框架在 flat-layout bench 上崩溃（html_generator）」
- **type**: known_bug_avoidance
- **severity**: medium
- **status**: pending

**Observation**:
cann-bench 的 HTML 报告生成器假定 `tasks/levelN/<op>` 布局；对 **flat 布局**的 bench suite
（如 `bench_lab/tilelang_ascend_bench/`，算子目录直接在 suite 根下）会崩溃，
且崩溃点在 stage 2 末尾 ⟹ **性能阶段根本不会执行**，整个评测以 rc=1 告终。
该 bug 同样影响同 suite 的 `gemm` 与 `flash_attention`。

**Evidence**:
`src/kernel_eval/report/html_generator.py:494`：
`levels_set.add(int(op.rel_path.split('/')[0][-1]))` —— flat 布局下 `rel_path == "r4_fused_sampling"`，
`split('/')[0][-1]` 取到字符 `'g'` ⟹ `ValueError: invalid literal for int() with base 10: 'g'`。
异常从 `save_all()` 冒泡到 `staged_eval._save_report()`，首次运行（rc=1）只产出 `.json`+`.md`，无 `.html`、无性能数据。
**不能靠把 `rel_path` 改成 `levelN/...` 来绕**：`BaselineStore._resolve_entry` 用 rel_path 各段当 JSON key，
而 metadata 是 flat key（`data["r4_fused_sampling"]["1"]`），加前缀会**静默把 28 个基线锚点全部变成 0.0**。
本周期只在 `PYTHONPATH` 层加 `sitecustomize.py` 包裹 `ReportGenerator.save_html`（`R4_HTML_SHIM=1` 才生效，
`finally` 恢复原值），不碰 `$R/src/`；分数经独立复算与报告一致到 Δ=0 / 7.1e-15，证明 shim 对数值无影响。

**Proposed change**:
记录规避条目：症状「flat-layout suite 评测 rc=1、只有 json/md 没有 html、性能阶段未执行」→
成因「`html_generator.py:494` 对 rel_path 首段取 `[-1]` 当 level 数字」→
规避「PYTHONPATH 层 sitecustomize 包裹 `save_html` 捕获该 ValueError；**禁止**改 rel_path 加 levelN 前缀（会静默清零基线）」→
上游修法建议「`seg = op.rel_path.split('/')[0][-1]; levels_set.add(int(seg)) if seg.isdigit() else None`」。
