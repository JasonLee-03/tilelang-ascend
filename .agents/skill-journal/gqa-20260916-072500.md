## Entry e4
- **target_skill**: tilelang-custom-skill/tilelang-programming-model-guide
- **target_artifact**: skill
- **target_section**: prim_func 编写约束（建议新增「解析期语义」小节）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
guide 没有说明 `T.prim_func` 体内三类语句的解析期差异，导致很容易写出「看起来是普通 Python
逻辑、实际编译不过或语义不同」的代码：
① `for x in range(...)` 是 **TIR 运行时循环**（`x` 是 `Var`），不是 Python 展开循环；
② 条件为 Python bool 的 `if` 在 **trace time 折叠**（只 trace 成立的分支，不发 IfThenElse）；
③ 分支体内绑定的名字**限定在该分支帧**，兄弟帧不可见、父帧可见。

**Evidence**:
developer 查证已安装 tvm 的 `tvm/script/parser/tir/parser.py`：`visit_for` 要求迭代器是
ForFrame（range / T.serial / T.unroll…），直接迭代 Python list 解析报错；`visit_if` 对
Python-bool 条件做 trace-time 折叠。实测两条硬证据（`examples/gqa/gqa.py` dense_expert scatter）：
`for si in range(len(segs)): ... segs[si]` → `error: list indices must be integers or slices, not Var`；
`s_f` 绑在兄弟帧 → `error: Undefined variable: s_f`，而同一处父帧的 `segs`、`s_l` 可正常解析
（报错只点名 `s_f`，正好印证「父帧可见 / 兄弟帧不可见」）。

**Proposed change**:
新增「prim_func 解析期语义」小节：三条规则 + 判别方法（迭代器必须是 ForFrame；Python 常量条件
会折叠；跨帧名字必须从父帧可见的容器就地重导出，或改为静态槽位展开），并给一组错误/正确对照示例。

## Entry e5
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: 新增「prim_func 变量解析错误（Undefined variable / list indices ... not Var）」条目
- **type**: runtime_error_recipe
- **severity**: high
- **status**: pending

**Observation**:
两类解析期报错缺少「症状 → 原因 → 解决」条目，排查成本很高（本次 Orchestrator 连续两次误判病因）。

**Evidence**:
症状 A：`error: Undefined variable: s_f`，箭头指向 prim_func 内 `if s > s_f:` 行
（`examples/gqa/gqa.py`，ruff 0.16.7 / site-packages tilelang 0.1.4+d75300ed）。
原因：`s_f` 由兄弟帧 `if len(segs) >= 1:` 内的元组解包绑定，TVMScript 把分支体绑定限定在该帧。
解决：从父帧可见的容器就地重导出（`s_first = segs[0][0]`），或把发射逻辑改为静态槽位展开。
症状 B：`error: list indices must be integers or slices, not Var`，指向 `segs[si]`。
原因：用 TIR 循环变量索引 host 侧 Python list（`for si in range(len(segs))` 的 `si` 是 Var）。
解决：不要用运行时循环变量索引 Python 容器；改为 trace-time 静态展开或展平成固定槽位。

**Proposed change**:
troubleshooting 增加上述两条三段式条目（各自附错误原文与最小复现结构）。

## Entry e8
- **target_skill**: tilelang-op-test-design
- **target_artifact**: skill
- **target_section**: 非对齐 / 需 padding 形状的覆盖规则
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
非对齐（需要 padding）形状若只用「pad 占比极小」的尾块用例（如 `S_kv - 4`），会系统性掩盖
pad 区域处理错误——此类误差与 **pad 占比成正比**，小 pad 恰好落在容差内，用例全绿但缺陷仍在。

**Evidence**:
gqa 的 decode 非因果路径存在既有缺陷：non-causal mask 分支只有 `mask_cpu = torch.zeros(...)`，
未把 pad 列置 `_BIG_NEG`（causal 分支有 `if S_kv < S_kv_padded: mask_cpu[:, row_idx, S_kv:] = _BIG_NEG`），
于是零填充的 K/V pad 列以 score=0 参与 softmax 撑大分母。实测 decode B2/S1/Nq32/Nkv8/D128 fp16：
Skv=100（pad 21.9%）maxdiff 5.518e-02 / 7702 违例；Skv=132（pad 48.4%）8.917e-02 / 7911；
Skv=300（pad 21.9%）2.612e-02 / 7285；而 Skv=380（pad 1.0%）1.038e-03 / **0 违例**、
Skv=2044（pad 0.2%）9.155e-05 / **0 违例**。现有 `test_gqa.py` L1 的 decode 尾块用例正是
Skv=2044，68 用例本地评测与 20 个 bench 用例（S_kv 全为 128 对齐）同样不覆盖 → 该缺陷历经
3 轮评测修复始终未暴露。判别性对照：同形状 causal 全部 0 违例。三方（交付版 / CI 基线 /
attempt-4）逐位一致，证明与本次两项改动无关。
发现路径值得记录：该缺陷不是被测试套件发现的，而是被 Orchestrator 的 A/B harness 发现——该 harness
对每个形状**同时**断言「新旧逐位一致」与「对 golden 的容差违例数」；只做前者会把既有缺陷当作正常放过。
已在 attempt 5 修复（host 侧 +2 行；pad≥20% 形状 tolviol 176..45903 → 0，15 个应不变形状逐位一致，
7 个 `_gqa_kernel_*` 工厂 AST 全等，24/24 回归通过），但**覆盖规则的空白仍在**。

**Proposed change**:
覆盖规则增加：「需要 padding 的非对齐形状，必须同时覆盖**大 pad 占比**（≥20%，如 S_kv=100→pad 128、
S_kv=132→pad 256）与**小 pad 占比**（如 S_kv-4）两类；只测尾块 4 行不足以验证 pad 区域语义。
若算子对 pad 区域依赖 mask/哨兵，还需覆盖『同一形状下 mask 生效与不生效』的对照（如 causal vs
non-causal）以定位屏蔽逻辑分支。」
