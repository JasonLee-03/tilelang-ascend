## Entry e1
- **target_skill**: tilelang-op-design
- **target_artifact**: skill
- **target_section**: 技术约束检测 / 随机算子的 RNG 独立性验证（新增「随机/采样算子」专项约束）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
op-design 对「随机/采样算子」缺少一条硬约束：**RNG 噪声必须验证统计独立性（equidistributed ≠ independent）**，
且应在 **Stage 1 用 CPU 预验证分布**（χ²/KL/自相关），不能只验 bitwise、把分布留到 Stage 2。R4 V01-b 首设计
沿用草稿的仿射 LCG `state_ij = seed_i + j`（+3 轮 `state=A·state+C`），断言「每元素独立（random_1d 范式）」——
该断言**错误**：仿射 LCG 满足 `LCG³(seed+j)=A³·(seed+j)+K`，使 `G_ij=f(seed_i+j)` 成**秩-1 行波相关场**，
违反 Gumbel-max（定理 T3）要求的 i.i.d. Gumbel 前提 ⟹ 采样分布崩坏，触发设计回退。

**Evidence**:
首轮 Stage 2 `[DESIGN_ERROR]`：kernel 逐位忠实实现设计（L0-A/L0-B/L1 tok_out int32 全 bitwise），但分布门禁
χ²=5058.68/dof=39（p≈0）、KL=3.42e-2、熵 rel 1.71e-1 灾难性失败；纯 CPU 复现设计公式 χ²=5057.6≈kernel（坏在公式）；
真·i.i.d. Gumbel 对照 χ²=31.3 p=0.80（方法论正确）；旧 LCG lag-2 自相关 **+0.977**。修复用 **lowbias32 avalanche hash**
`state=lowbias32(seed_i·PRIME_W+j)` ⟹ CPU 预验证 χ²=26.58 p=0.935、lag-1/2/5≈0.005、NPU 复现 χ² p=0.9807。
（`debug_log.md` Attempt1(V01-b)、`DESIGN_v01b.md` §0.0.1/§0.0.4）

**Proposed change**:
在 op-design 的技术约束检测新增「随机/采样算子」专项：① RNG 若用于 Gumbel-max / 拒绝采样等需 i.i.d. 的场景，
**禁用纯仿射 LCG（线性 ⟹ 秩-1 相关）**，改用非线性 counter-based avalanche hash（lowbias32 / splitmix / murmur finalizer）；
② **Stage 1 必须用 CPU 预验证噪声分布**（χ² p>0.01 / KL / 自相关 / 熵 vs 目标），达标才定稿，不得只验 bitwise 或推迟到 Stage 2；
③ 明确「equidistributed（均匀）≠ independent（独立）」的判据。

## Entry e2
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: dav_c220 int32 位运算原语约束（And/Or/Xor/Not/ShiftRight）
- **type**: error_code_workaround
- **severity**: high
- **status**: pending

**Observation**:
dav-2201(A3)/dav_c220 上 int32 位运算原语有多项硬约束，直接照搬 uint32 hash 会失败或**静默算错**：
① `AscendC::And`/`Or` **仅 int16/uint16**；TileLang 对 int32 调 `bitwise_and`(buffer⊕buffer) **能编译但运行时 halving**
（count 按 int16 消耗 ⟹ 只处理 M/2 个 int32：128→64、256→128、4096→2048，精确半数）；② int32 `bitwise_xor`/`bitwise_not`
**编译失败**；③ **无 scalar-and**（`tl.ascend_bitwise_ands` 未注册）；④ `bitwise_rshift` 对 int32 是**算术右移（符号扩展）**非逻辑。

**Evidence**:
C++ static_assert `kernel_operator_vec_binary_impl.h:390/457`、CANN `xor.h:59-60`（仅 int16_t/uint16_t）；
developer 运行期探针 `r4_and_probe`/`r4_binop_scope` 实测 int32 And halving（rounds=1 plain[M] 半数错、over-alloc mism=0）；
`xor`/`not` int32 编译失败、scalar-and「Operator tl.ascend_bitwise_ands is not registered」。（`debug_log.md`、`DESIGN_v01b.md` §0.0.3）

**Proposed change**:
新增故障条目「症状：int32 `bitwise_and` 结果只有一半元素正确 / int32 `bitwise_xor`·`not` 编译失败 / `bitwise_rshift` 符号扩展 →
原因：dav_c220 And/Or/Xor/Not 仅 int16/uint16，int32 And 运行期 halving，ShiftRight 是算术 →
解决：**over-allocation**（操作数声明 int32[2·BV]、数据放 [0:BV)、count=2·BV ⟹ 处理 2·BV int16 = BV int32 全覆盖）；
XOR 用 `x^t = x+t−2·(x&t)`（add/and/mul/sub）；逻辑右移用 shift-trick `x>>>s = a−((a>>(32−s))<<(32−s))`（仅 rshift/lshift/sub，免 and）」。

## Entry e3
- **target_skill**: tilelang-op-design
- **target_artifact**: skill
- **target_section**: §API 检索/技术约束检测——原语可用性探针方法（compile-only 不足）
- **type**: unclear_workflow
- **severity**: high
- **status**: pending

**Observation**:
op-design 核实 API/原语可用性时若只做 **compile-only 探针**（`tilelang.compile(...)` 成功即判「可用」）会漏掉**运行期语义错误**。
R4 V01-b rev1 设计据此把 int32 `bitwise_and`(buffer⊕buffer) 判为「✅ 可用」，但它在运行时 halving（只处理半数元素）——
编译通过但结果错。该缺陷直到 Stage 2 运行期才被 developer 发现，差点造成二次失败。

**Evidence**:
developer rev1 报告：「design §0.0.3 的『buffer⊕buffer int32 and 可用』基于 **compile-only 探针（不验运行）+ 误读
`per_block_cast:262`（实为 scalar-and）**」；运行期探针 `r4_and_probe` 才暴露 halving。（`debug_log.md`、`DESIGN_v01b.md` §0.0.3 修订）

**Proposed change**:
在 op-design 的 API 检索/约束检测流程明确：原语可用性核实**必须含运行期验证**（实跑最小 case + 对拍数值），
`tilelang.compile()` 成功**不等于**运行正确；尤其 int32/低层位运算·归约·搬运类原语，须运行期探针确认 count/scope/语义，
并交叉核对引用的 example 行是否真是同形态（避免把 scalar-and 误当 buffer⊕buffer）。

## Entry e4
- **target_skill**: tilelang-op-test-design
- **target_artifact**: skill
- **target_section**: 随机/采样算子的验证方法论（两层：bitwise 忠实参考 + 分布一致性）
- **type**: unclear_workflow
- **severity**: medium
- **status**: pending

**Observation**:
op-test-design 缺少「随机/采样算子」的验证方法论。此类算子输出**不可对拍框架 op**（如 tok_out vs `torch.multinomial`，
因 RNG 流不同），但**可对拍「忠实参考」**（同 RNG/同算法/同 seed 的 Python 镜像）⟹ 应设计**两层**：
① **bitwise 对拍忠实参考**（L0 主判据，能精确定位 RNG/变换/argmax/归并任一环节 bug）；② **分布一致性**（χ²/KL/覆盖率/熵，
多 seed N≈100k，验证「正确 RNG ⟹ 服从目标 categorical」）。另需注意**大 keep 集（k≥256）在 N=100k 时 KL 因空-bin 有限样本偏差偏高**
（非算子缺陷），须用 N≥400k 或 KL-over-observed-bins。

**Evidence**:
R4 V01-b §9 两层验证：L0-A（hash int32 state vs golden_hash 逐位）+ L0-B（tok_out vs golden_gumbel_sample 逐位，11 次运行 mism=0）；
分布 NPU 实测 χ²=22.98/dof=39 p=0.9807、KL=7.82e-4、cov=1.0、熵 rel 2.02e-3 全达标；`DESIGN_v01b.md` §9.5 记录大 keep 集有限样本偏差指引。

**Proposed change**:
在 op-test-design 增「随机/采样算子」验证章节：① 优先构造**忠实参考**做 bitwise L0（即使无法对拍框架 op）；
② 分布一致性作 L1/L2（χ² p>0.01 / KL<1e-3 / 覆盖率>1-1e-4 / 熵 rel<1%，给 N 与门槛）；
③ 提示大支撑集下 χ²/KL 的空-bin 有限样本偏差（提高 N 或对 observed bins 归一），避免误判失败。

**Observation**:
hash/魔数常量手写十进制易转写出错。R4 V01-b 设计 §3.3 把 lowbias32 的 `HASH_M2` 十进制写成 `-2073151861`

但 kernel 若照抄设计的十进制会算错——developer 靠权威 golden 逐步隔离才定位到 `r2=xo·M2` 的有效乘数是 0x846E368B。

**Evidence**:
developer rev1 报告「定位：权威 golden 逐步隔离 t✅/xo✅/**r2=xo·M2❌** → Python 反推有效乘数=0x846E368B」；
修复：kernel 改从 hex 经 `ctypes.c_int32` 推导常量。（`debug_log.md`、`DESIGN_v01b.md` §3.3 修订）

**Proposed change**:
在 op-develop 实现规范补一条：int32 魔数/hash 常量**一律从 hex 字面量经 `ctypes.c_int32(...)`（或等价）推导**，
禁止手写十进制转写；设计文档给出常量时以 hex 为准，十进制仅作注释且须由工具生成核对。

## Entry e6
- **target_skill**: tilelang-op-design
- **target_artifact**: skill
- **target_section**: UB 内存预算校验（memory_planning 别名 ⟹ 静态和是上界，须以编译 UB 报告为准）
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
UB 预算若只把各 buffer 大小**静态求和**会**高估**：`tl.ascend_memory_planning` 会对**生命周期不重叠**的 buffer 做别名复用。
R4 V01-b rev1 因 int32 And over-allocation 使 hash 的 3 个 `[2·BV]` int32 buffer 静态和 ≈192.6KB **超过 184KB**，
但 memory_planning 把 `h_ub`/`tmp_ub` 与 Gumbel 期的 `g_ub` 别名（生命周期不重叠）⟹ **实测 ≤184KB**，V-b0 编译+运行 OK，
无需降 BV=2048。设计不应仅凭静态和超限就否决方案或降 BV。

**Evidence**:
`DESIGN_v01b.md` §4.5（V01-b.2 修订）：「over-alloc 后保守静态 ≈192.6KB 超限 → memory_planning 别名 h_ub/tmp_ub↔g_ub 后实测 ≤184KB，
V-b0 上板编译+运行 OK，无需降 BV=2048，『BV=4096 可行』结论不变」；developer V-b0「BV=4096 over-alloc COMPILE_OK + 运行」。

**Proposed change**:
在 op-design 的 UB 容量校验补一条：静态 buffer 求和是**上界**，`ascend_memory_planning` 会别名不重叠生命周期的 buffer ⟹
实际占用可能显著更低；当静态和略超 184KB 时，**先以编译期 UB 报告 / 上板最小 case（如 V-b0）核实实际占用**，
再决定是否降 BV，不要仅凭静态和否决。（与 V01-a journal e4「topk 自动 tmp arena 勿低估」互补：一为勿低估、一为勿高估。）
