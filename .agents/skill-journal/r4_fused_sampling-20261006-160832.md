## Entry e1
- **target_skill**: tilelang-custom-skill/tilelang-env-check
- **target_artifact**: skill
- **target_section**: 完整工作流 / 步骤 4「运行测试验证」（`source set_env.sh && python quick_verify.py`）
- **type**: unclear_workflow
- **severity**: high
- **status**: pending

**Observation**:
env-check 的固定流程「source set_env.sh → 跑 quick_verify → 失败则拉子模块+install_ascend.sh 重编译」在
「已存在可用 tilelang wheel + 仓库源码未编译」的环境下会误判并触发不必要的重编译。本环境已装
`tilelang 0.1.4+cann920` wheel（自带 tvm、含全部 T.tile.* API），而仓库 `tilelang/` 源码无 `build/`、
子模块全部未初始化。`source set_env.sh` 把仓库根加进 PYTHONPATH，使未编译的仓库源码 shadow 掉可用 wheel，
`import tilelang` 直接 `ModuleNotFoundError: No module named 'tvm'`，按 skill 流程会被判为「测试失败 → 拉子模块重编译」（20~40 分钟且可能失败）。

**Evidence**:
从仓库根 `python -c "import tilelang"` → `No module named 'tvm'`（`tilelang/__init__.py:65 import tvm`）；
从中立 cwd（`.agents/skills`）同一命令 → 成功解析到 `~/.local/lib/python3.12/site-packages/tilelang`。
`git submodule status` 全部 `-` 前缀（3rdparty/tvm 等未初始化）；无 `build/` 目录。
不 source set_env.sh、改设 `ACL_OP_INIT_MODE=1` + `TILELANG_CACHE_DIR` 后 quick_verify.py exit 0。

**Proposed change**:
在步骤 4 之前增加一个「运行时来源判定」：先从中立 cwd 探测 `python -c "import tilelang,os;print(os.path.dirname(tilelang.__file__))"`，
若已解析到可用 wheel（site-packages）且仓库源码未编译（无 build/、子模块未初始化），则**不要 source set_env.sh**、
以中立 cwd + `ACL_OP_INIT_MODE=1` 跑 quick_verify，且**不触发**子模块拉取/重编译；仅当 wheel 不可用或 quick_verify 真失败时才走重编译流程。

## Entry e3
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: reduce / real_shape 窄归约（narrow-reduce）编译失败
- **type**: runtime_error_recipe
- **severity**: high
- **status**: pending

**Observation**:
`T.reduce_max/reduce_sum` 的 `real_shape=[1,valid]` 窄归约、以及列切片 BufferRegion `reduce(buf[:,0:valid],…)`，
都受 codegen 硬约束：逻辑宽度 `nn*elem_bytes <= 256`（= **64 个 fp32**）。尾块 valid>64（R4 尾块 valid=512）时主方案与
BufferRegion 兜底**都编译失败**（同一 narrow 路径）。解法：为尾块分配**精确尺寸 `[1,TAIL]` 缓冲 + 全量 reduce（不传 real_shape）**，走 normal reduce 路径。

**Evidence**:
`debug_log.md` V-2：`InternalError: Check failed: (nn * elem_bytes <= 256) ... got 512 elements of 4 bytes`（`src/target/codegen_ascend.cc:2145`）。
兜底已验证：V=152064、BV=4096（37 满块 + 512 尾块）online-softmax m/s 与 CPU 对拍正确（m 逐位相同、s rtol<1e-3）；
`example_online_softmax` 已证 block_N=128 fp32=512B>256 的**全量** reduce 可用。

**Proposed change**:
新增故障条目「症状：`Check failed: (nn*elem_bytes<=256)` 编译错 → 原因：real_shape/列切片 narrow-reduce 逻辑宽度上限 256B(64 fp32) →
解决：尾块改精确尺寸 [1,TAIL] 缓冲做全量 reduce，不用 real_shape/BufferRegion 窄归约」；并在 reduce 的 real_shape 文档处标注该 256B 上限。

## Entry e4
- **target_skill**: tilelang-op-design
- **target_artifact**: skill
- **target_section**: 技术约束检测 / UB 容量预算（含 topk/sort 的自动 tmp arena）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
op-design 的 UB 预算指导未覆盖 `T.tile.topk`/`T.tile.sort` 会**自动注入 tmp arena**这一项。R4 草稿把 topk 相关 UB 估为 7KB，
实际 fp32 topk 的自动 tmp arena = `factor(=4) × AlignUp(max_actual_num,32) × sizeof(fp32)=4B` = **64KB**（且编译器对多个 op 取 **max** 而非 sum，
单一共享 shared.ub arena）。低估约 3 倍导致草稿误判 S1'(BV=8192)≈73KB 可行，实际 ≈233KB > 184KB 不可行。

**Evidence**:
`DESIGN.md §3.5.4 / §10.4 修正 5-6`：`src/transform/allocate_tmp_buffer.cc:578-596`（`GetAscendCWorkspaceSpec`，fp32 topk factor=4，
`count=ceil(max_actual_num/32)*32`）+ `:1195-1206`（`GetTmpBufferSize_` 取 `std::max` 非 sum）；推出闭式约束 `28·BV + 36·K_MAX + 72 ≤ 188416`，
K_MAX=256 时 BV≤6400（草稿 BV=8192 的 S1/S2' 均超限）。

**Proposed change**:
在 op-design 的 UB 容量校验章节补一条：使用 `T.tile.topk`/`T.tile.sort` 时，UB 预算必须计入自动 tmp arena
`= factor × AlignUp(max_actual_num,32) × sizeof(dtype)`（fp32 topk factor=4），且多 op 取 max（共享单一 arena），并给出该公式与一个算例。

## Entry e6

- **target_artifact**: troubleshooting
- **target_section**: 纯 Vector kernel 的标量运算（alloc_var / 标量 exp·log / 二元 max）
- **type**: known_bug_avoidance
- **severity**: high
- **status**: pending

**Observation**:
纯 Vector kernel 内标量处理有多个坑：① `T.alloc_var` 标量重绑定（`v = A[cid]`）**能编译但结果错误**（返回 0.0）；
② `T.alloc_var(init=T.infinity())` 被拒（"only accept int or float"）；③ 标量 `T.exp`/`T.log` **无法 codegen**
（"Unresolved call Op(tir.exp/log)"）；④ `T.max(a,b)` 直接对 buffer 元素调用失败。规避：全部标量改用 `[1]`/`[1,1]` `alloc_shared` buffer，
算术全用 `T.tile.*`（exp/ln/sub/mul/div/max/broadcast），running-max 用 `T.tile.max(dst,s0,s1)`，GM 标量读写用 `T.copy(region)`。

**Evidence**:
`debug_log.md` 附加发现 1、4、6：alloc_var 重绑定返回 0.0；`T.alloc_var(init=T.infinity())` "only accept int or float"；
标量 exp/log "Unresolved call Op(tir.exp/log)"；probe B1/B2/B3、probe_loop C1 实测 `[1]`/`[1,1]` alloc_shared + T.tile.* 正确
（`example_online_softmax`/`cross_entropy` 既有生产范式印证）。

**Proposed change**:
新增故障条目「症状：alloc_var 标量返回 0 / 标量 exp·log 'Unresolved call Op(tir.exp/log)' / T.max 对 buffer 元素失败 →
原因：纯 Vector kernel 标量语义不可靠 → 解决：标量一律用 [1]/[1,1] alloc_shared buffer + T.tile.* 运算 + T.copy(region) 读写 GM 标量」。

## Entry e9
- **target_skill**: tilelang-op-develop
- **target_artifact**: troubleshooting
- **target_section**: 空循环体导致的死 buffer（T.serial(0)）编译错
- **type**: error_code_workaround
- **severity**: medium
- **status**: pending

**Observation**:
当分块循环次数在编译期为 0（R4 中 V<BV ⟹ `n_blk_full=0` ⟹ `T.serial(0)` 消除满块循环体）时，只在循环体内使用的 buffer
成为死 buffer，内存规划不分配地址，编译报 "Cannot find pre-allocated address for buffer: z_ub"。规避：把这些 buffer 的分配
移入编译期 `if n_blk_full > 0:` 守卫（与循环体同域）。V=256 属支持域，必须能跑纯尾块路径。

**Evidence**:
`debug_log.md` L0 失败 #3：`l1_edge_V_eq_KMAX`(B=2,V=256) 编译 `InternalError: Cannot find pre-allocated address for buffer: z_ub`
（`codegen_ascend.cc:828`）；修复为 4 个 BV 尺寸 buffer 移入 `if n_blk_full > 0:`，已验证 V=256/512 纯尾块路径 5 输出全对。

**Proposed change**:
新增故障条目「症状：'Cannot find pre-allocated address for buffer: X'（X 只在循环体内用）→ 原因：编译期 trip count=0（如 T.serial(0)）消除循环体使 X 成死 buffer →
解决：把 X 的分配放进与循环体同域的编译期 `if <trip> > 0:` 守卫」。

## Entry e10
- **target_skill**: tilelang-op-test-design
- **target_artifact**: skill
- **target_section**: L0 门槛测试计划 / 测试数据生成（带守卫·降级路径的算子）
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
对含**守卫/降级路径**的算子（R4 的 `valid`：nucleus>K_MAX 时守卫触发、整批回退），L0 快路径用例的测试数据必须保证**守卫不触发**
（参考输出 valid 全 1），否则 L0 会因守卫触发而「假失败」，极易误判为 kernel bug 甚至误报 [DESIGN_ERROR]。R4 中裸 `randn` logits 的
p=0.95 nucleus 达 112793 ≫ K_MAX=256，必须把 logits 放大到 `LOGIT_SCALE=8.0` 才能让全部 L0 用例 valid_ref=1。

**Evidence**:
`DESIGN.md §9.2.1`（强制 LOGIT_SCALE=8.0，含逐 scale 实测表：scale 1/3/5/6/7 均有行 valid=0，仅 8.0 全过、nucleus 余量≥3.7x）；
`debug_log.md` L0 失败 #1（`l0_prod_v_tail`/`l0_full_occupancy` valid ratio 0.9375/0.9250、valid_ref 非全 1，根因是数据使守卫触发）。

**Proposed change**:
在 op-test-design 的 L0/测试数据生成指导中补一条：对带守卫/降级/回退分支的算子，L0 快路径用例必须构造「守卫不触发」的输入
（参考断言 valid/keep-all 成立），并在计划里写明数据配方与理由；显式警告「守卫触发导致的 L0 失败不是 kernel bug，先查数据配方」。
