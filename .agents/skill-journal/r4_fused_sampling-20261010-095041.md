## Entry e1
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: `references/performance-antipatterns.md`（新增条目；与既有「冗余全局同步」L154-196、「正交轴串行化」L420-459 并列）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
现有反模式清单**漏掉了本周期收益最大的一个模式**：`T.Parallel(N)` 在 N 较小（1-D、256 量级）时被 codegen
降级为 N 次标量 `GetValue/SetValue`，且**每轮插入 1~2 个 `PipeBarrier<PIPE_ALL>`（全流水 drain）**。
漏掉的根因不是"没写这条"，而是**既有两条相邻反模式的「识别特征」都锚定在 Python 源码层**：
「冗余全局同步」的识别特征是源码里出现 `T.barrier_all()` / `T.sync_all()`（开发者手写的），
「正交轴串行化」的识别特征是"两层嵌套循环 + 内层标量 `if`/`GetValue`/`SetValue`"。
而本例开发者写的是 `T.Parallel(256)` —— **在源码里看起来已经是向量化的、单层的、没有手写 barrier**，
两条识别特征都不匹配，照清单逐条对照会判为"无此反模式"。该缺陷只能在 `get_kernel_source()` 层被发现。

**Evidence**:
`examples/R4/perf_tuning/optimization_log.md` L34-35：`get_kernel_source()` 实证 K1.cc L169-178 / L184-193
两个 `T.Parallel(K_MAX)` tie_m 填充循环被降级为 256 次标量 `GetValue/SetValue`，每轮 1~2 个 `PipeBarrier<PIPE_ALL>`。
改写为 `broadcast + compare + select + reduce_sum` 后 `PipeBarrier_ALL` 计数 **768 → 5**（同文件 L154）。
源码侧 grep 确认：`performance-antipatterns.md` 全文无 `PipeBarrier` 字样，
`optimization-guide.md` 仅在 L1119 提到 `AUTO_SYNC=True` 下编译器自动插入 `PipeBarrier<PIPE_V>`（不同 pipe、不同成因）。
效果：该项与 [#2] 合计使 fused 18 case geomean 提速 1.5386×、mask 1.4242×，36/36 case 无一回退。

**Proposed change**:
新增反模式条目「编译器插入的 `PipeBarrier<PIPE_ALL>`：小范围 `T.Parallel` 的标量降级」，
**识别特征必须写在生成代码层**（`get_kernel_source()` 中统计 `PipeBarrier<PIPE_ALL>` 出现次数，
以及 `GetValue`/`SetValue` 是否出现在本应是向量的位置），并显式加一句与既有两条的区分说明：
「源码写成 `T.Parallel` / 单层循环 **不排除**本模式——`T.Parallel` 不保证向量化，小范围 1-D 会被标量化」。
替代方向指向 §2.15 正交轴向量化（broadcast+compare+select+reduce_*）。

## Entry e3
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: SKILL.md Step 5「效果验证」（L142）与 Step 4 子步骤 C
- **type**: unclear_workflow
- **severity**: high
- **status**: pending

**Observation**:
Step 5 只写了"每个优化点后执行：精度验证 → `msprof op` → 记录 → 对比基线"，
**"精度验证"是哪一层完全没定义**。核心约束区（L20-24）也只说"精度未通过禁止性能优化"，没说通过的标准是什么。
这在算子带有分层测试套件（L0/L1/L2/Boundary/stability/stress）时是个实质缺口：
① 不同层的检出力差别极大——`--level all` **不包含** stress（UB 投毒）层；
② 性能优化最常见的正确性风险恰恰是**改变了归约顺序 / 消除了看似冗余的填充或 pad**，
这类改动在良性未初始化内存上完全无症状，只有投毒层能确定性检出；
③ 若优化点自称"bitwise 等价"，skill 没要求给出 bitwise 证据，只要求"精度 pass"，
而容差型 pass 无法区分 bitwise 等价与舍入路径改变。

**Evidence**:
本周期 Orchestrator 在调度 prompt 中必须**自行补齐**这一契约（额外强制 `--level stress`），
理由直接来自上一周期记录的残留缺口：`.orchestrator_state.json → resolved_failure.root_cause_ESTABLISHED.residual_risk`
明确写「`--level all` does NOT include the stress (UB-poison) layer … 单次通过不构成证据」。
实测四门禁（kernel `ac8eba47`，2026-10-10，均 exit 0）：
`--level all` → 74 PRECISION_PASS / 0 FAIL + 38 BOUNDARY_PASS / 0 WARN；
`--level stability` → tail-adversary 哨兵扫描 TAIL=257/511/261 全部 `dropped=0`；
`--level stress` → 8/8 UB 投毒配置 × 200 reps，`selfdiff=0 goldenfail=0 invariant=0`；
`coverage_check.py` → 25 PASS / 0 MISS / 0 N/A。
其中 stress 层是[#2]「消除 topk(K=1)」这类改动的**唯一确定性防线**——该改动删掉了一次全排序，
若排序顺带掩盖了脏 UB，只有投毒能暴露。SKILL.md 全文（含 references/）无 `--level` / 分层门禁字样。

**Proposed change**:
Step 5 增加「精度门禁契约」小节：① 明确"精度验证"= 跑**该算子测试套件的全部分层**，
并逐一列出 exit code 与 PASS/FAIL 计数，不允许只跑默认层；
② 硬性提醒：若套件存在 UB 投毒 / poison / stress 类层，**它通常不在 `all` 里，必须单独跑**，
理由是"性能优化常删改 pad/填充/排序，这类改动在良性未初始化内存上无症状"；
③ 若优化点声明 bitwise 等价，必须附 bitwise 证据（`matched_ratio=1.0` 且 `max_abs=0`，或 tok/idx 逐元素相等），
容差型 pass 不构成 bitwise 等价的证据；④ 门禁失败时按既有规则"保持优化调试，不撤销"，但需回滚到上一个
`history_version/` 备份点而非手工重敲。

## Entry e7
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: skill
- **target_section**: `references/api-compute.md` §4.12 `T.tile.topk(dst, src, K, actual_num)`（L695-716，「注意事项」L715-716）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
`T.tile.topk` 的文档**只有对齐约束，没有代价模型**。现「注意事项」仅一条："`src` 的大小需要满足32或32的整数倍"。
缺失的关键事实：topk **没有 partial-select 路径**，`topk(K=1, N)` 会对整个 N 做**完整 Sort** 再取第 1 个。
这让"只要最大值/最小值及其索引"的场景付出 O(N log N) 全排序代价，而正确做法是
`reduce_max + compare(EQ) + select + reduce_min`（O(N)，且 `optimization-guide.md` §2.15 已有该方法论，两边无交叉引用）。
另有一条更严重的遗漏：`count`（`actual_num`）**非 32 倍数**时，`tl::ascend::Sort()` 修补余数用的
masked `AscendC::Duplicate` 在 dav_c220 上**不生效**，会把未初始化 UB 槽位当真实候选排序——
文档只说"需要满足32或32的整数倍"，没说违反后果是**静默的数值错误**而非报错。

**Evidence**:
代价模型：`examples/R4/perf_tuning/optimization_log.md` L40、L156 —— [#2] 「K2g 每块 `topk(K=1)` 全排序」，
`topk(1, 4096)` 对 4096 元素做完整 Sort 仅取 1 个 max；改 `reduce_max+compare(EQ)+select+reduce_min` 后
**TopK/Sort 调用归零**，为 mask 任务 geomean 1.4242× 提速的主要来源之一。
"无 partial-select 原语"由本周期 [#6]（`topk(256)` 优化）判定不可实施时确认。
bitwise 等价性已验证：max 精确无舍入 → `blk_max == topk_dst[0]`；tie 时 `reduce_min` 取最小 index，
与 `torch.argmax` first-occurrence 及 V-b4 验证的 `topk(K=1)` 行为一致（L165）；
L0-B gumbel `tok_out` bitwise `ratio=1.0 / max=0`。

导致脚本化核对时**朴素的 `grep -c MISS` 会返回 1 而不是 0**——即"零 MISS"和"有一处 MISS"在计数上不可区分，

**Evidence**:

供门禁脚本直接解析，不再 grep 文本；② 汇总行改为不含裸关键字的形式（如 `COVERAGE: pass=25 miss=0 na=0 -> PASS`）
