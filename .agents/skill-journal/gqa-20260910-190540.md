## Entry e1
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: "运行时错误.非确定性输出/随机 NaN（d2d→launch 竞态）"
- **type**: known_bug_avoidance
- **severity**: high
- **status**: pending

**Observation**:
tilelang kernel launch 与前置 torch NPU 端拷贝（padding 的 slice 赋值 / Mask_full 构造
等 d2d ViewCopy）之间的流序不可靠：kernel 输入逐位相同（Spy 验证）而输出非确定、
随机出现 NaN——症状为 checker 报 "NaN位置不匹配" 且 MERE/MARE 全 0，且在 warmup+
perf 多次调用下可升级为 SIGSEGV（评测 84-100 连环 rc=-11 的最可能机制）。

**Evidence**:
评测 gqa_67（MERE=0, MARE=0, mismatch=0, total=0，NaN 位置不匹配）与 gqa_84-100
rc=-11；examples/gqa/eval_fix_verify/dbg_nondet13.py：固定输入 + launch 前同步后 6/6
位稳定，同一输入 R2 基线代码随机 NaN。修复见 gqa.py `_npu_sync_tensor`（仅在有
padding 的路径的三个 torch→launch 边界插入同步，对齐路径字节级不变）。

**Proposed change**:
新增 troubleshooting 条目："wrapper 中先做 torch d2d 拷贝（slice 赋值/contiguous/
cat 替代方案）再立即 launch tilelang kernel → 输出非确定/随机 NaN/可能段错误 →
launch 前对涉及的 NPU 张量同步（如 torch.npu 侧 sync 或等价手段），并给出本 case
的最小复现模式与修复位置"。

## Entry e3
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: skill
- **target_section**: softmax/attention 类 kernel 的 mask 常量与归约顺序
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
加性 mask 常量 -(2^30) 在满量程 value_range（fp16 ±65504，D=128 点积可达 ~5.5e11）
下会被原始 score 压制，产生两种静默错误：(i) W5（max-after-mask）kernel 中被 mask
列赢下 running max → 因果行"看到"未来 token；(ii) max-over-RAW kernel 中被 mask
列抬高 max → 全部可见权重 exp 下溢 → 输出全 0。且 mask 与 running max 的先后顺序
（W5 vs RAW）在各 kernel 间必须统一。

**Evidence**:
examples/gqa/eval_fix_verify/dbg_decode_causal.py：修复前 fp16 causal 满量程
mere=3.7（W5 型错误）、decode-causal 满量程 mare=1.0（RAW 型错误）；修复（`_BIG_NEG`
→ -1e30 + 全 kernel 统一 W5 顺序 + running-max 哨兵 + decode mask 负切片 clamp）
后 g2_special_values.py 满量程全 PASS（mere=0）。

**Proposed change**:
在 softmax/attention 章节新增"加性 mask 常量选择"约束：mask 幅值必须压制一切
有限 fp32 score（推荐 -1e30 而非 -(2^30)）；并要求 online-softmax 各 kernel 统一
"先 mask 后 running max"（W5）顺序、running-max 初始化用 sm_scale·mask 哨兵，
附满量程 value_range 的测试建议（cann-bench L1 case 10 的 [-65504,65504] 语法）。

## Entry e4
- **target_skill**: tilelang-op-develop
- **target_artifact**: skill
- **target_section**: 算子实现 / dispatch 设计章节
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
评测机（CANN 9.1 + tilelang 自建版）与本地（CANN 9.2 + pip 0.1.4）的编译器行为差异
无法靠本地枚举覆盖（上轮 per-head 58/58 本地可编译、评测机仍失败）。tilelang JIT
工厂在构造期急切编译，编译异常（TVMError/RuntimeError）在工厂调用处抛出——这使
"dispatch 处 try-except 编译回退链"成为弥合版本差异的结构性手段。同时 L0C/UB 有
静态预算：per-head 形态 `acc_o_l0c = (2·BM·BN + 2·BM·D)·4B`，超 192KB 即在
AscendMemoryPlanning 报 "Memory allocation failed for: acc_o_l0c"（评测 gqa_56
本地逐字复现：D=512@BM=64 → 262144B）。

**Evidence**:
评测 gqa_56（`acc_o_l0c required: 262144, new memory available: 0`）与 gqa_68
（bisheng Compilation Failed，多 kernel 均失败）；examples/gqa/eval_fix_verify/
g3_l0c_enum.py（本地复现）、g3c_fallback_selftest.py（回退链 4/4 自测）；gqa.py
prefill/decode 回退链实现（编译失败按候选序回退 + 进程级缓存，结构上不可能掩盖
精度/运行期错误——那些在 kernel 执行期抛出）。

**Proposed change**:
在 op-develop 的 dispatch/实现章节补充：(1) 提交外部评测的算子应实现"编译回退链"
（多候选 kernel + block_M 等降参阶梯，try-except 捕获编译期异常并缓存选择），
以结构性排除目标环境编译器差异；(2) 给出 L0C/UB 静态预算公式与常见形态
（per-head/g2/dense 的 acc_o_l0c 组成），要求实现前手算预算避免 256KB 上限。
