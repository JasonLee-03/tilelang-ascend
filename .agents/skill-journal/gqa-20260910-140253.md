# Skill Feedback - gqa（CANN-Bench 在线评测失败修复）

任务背景：gqa 算子在线评测 80 case 中 29 失败（cann_final_eval_20260909_102400），
Orchestrator 根因分析后调度 developer 修复（4 类：aclnn Transpose/ZerosLike 561103、
全 mask 行 NaN、g2 编译失败、连环 SIGSEGV），本地 132/132 精度回归通过。

## Entry e1
- **target_skill**: tilelang-custom-skill/tilelang-env-check
- **target_artifact**: skill
- **target_section**: 第四步 环境变量检查 / source set_env.sh 修复动作
- **type**: unclear_workflow
- **severity**: medium
- **status**: pending

**Observation**:
本机同时存在 pip 版 tilelang（0.1.4+ubuntu.24.4.cann920）与源码树（未编译、tvm 子模块未构建）。
skill 的自动修复动作 `source set_env.sh` 会把源码树 `$TL_ROOT` 前置到 PYTHONPATH，
导致 import tilelang 直接失败，且 skill 未覆盖"pip 版与源码树共存"这一场景的判别方法。

**Evidence**:
`source set_env.sh` 后运行 `import tilelang` 报
`ModuleNotFoundError: No module named 'tvm'`（加载路径 /mnt/.../tilelang-ascend/tilelang/__init__.py line 65）；
`unset PYTHONPATH` 后 pip 版正常（tilelang 0.1.4+d75300ed, torch_npu 2.7.1.post4, npu count 2）。
本次任务的全部本地验证必须以"不 source set_env.sh"为前提。

**Proposed change**:
在环境检查流程中增加一步：检测 pip 版 tilelang 是否已存在且可用；若可用且用户工作在
examples/ 算子修复场景（与评测形态一致），提示跳过 `source set_env.sh`，仅在源码开发
场景才 source，并说明两者的 PYTHONPATH 遮蔽关系。

## Entry e2
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: troubleshooting
- **target_section**: "运行时错误.aclnn 561103 算子 binary 缺失"
- **type**: error_code_workaround
- **severity**: high
- **status**: pending

**Observation**:
CANN 9.1.0 / Ascend910_9362 评测 SoC 包缺失多个常用 aclnn binary：Transpose、
ZerosLike（aclnnInplaceZero）、ConcatD / Cat_1_SliceAiCore、BroadcastToAiCore、GatherV3。
wrapper 层任何 `q.transpose(1,2).contiguous()`、`torch.zeros(..., device=npu)`、
`torch.cat` 调用都会以 error code 561103 崩溃，且本地 CANN 9.2 无法复现（版本差异）。

**Evidence**:
评测结果 gqa_31/50/56/57（`call aclnnInplaceCopy failed ... Op Transpose does not has any binary`）、
gqa_71/72/73/81（`call aclnnInplaceZero failed ... Op ZerosLike does not has any binary`）；
gqa.py:3144-3146 已有作者注释记录缺失清单。已验证安全的替代模式：CPU 构造 + 单次
`.to(device)` H2D、`torch.full`（FillScalar）+ slice 赋值（ViewCopy）、自写 tilelang
transpose kernel（含 tail 模式）；验证脚本 examples/gqa/eval_fix_verify/f12_op_guards.py
10/10 PASS。

**Proposed change**:
新增 troubleshooting 条目"错误码 561103 / Op XXX does not has any binary → 该 SoC 包缺
aclnn binary，列出已知缺失清单与三类替代模式（CPU+H2D / full+slice / 自写 kernel），
并提示本地新版本 CANN 无法复现、需按代码路径审查规避"。

## Entry e3
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: skill
- **target_section**: 归约/softmax 相关 API 章节
- **type**: missing_constraint
- **severity**: medium
- **status**: pending

**Observation**:
带 causal-skip 的 online-softmax kernel 中，全 mask 行（causal 且 S>S_kv 的前 S-S_kv 行）
sumexp=0，最终 normalize 0/0=NaN；而评测 golden（cann-bench golden.py F217，与
sparse_flash_attention 对齐）要求全 mask 行输出 0。skill 未讲 softmax 类 kernel 的
NaN 语义对齐与保护写法。

**Evidence**:
评测 gqa_67 "MERE=0.000000, MARE=0.000000 ... NaN位置不匹配"（其余位置 bit-exact，
正是 0/0=NaN 的指纹）；修复为 normalize 前 `T.tile.add(sumexp, sumexp, 1e-30)`
（T.tile 标量常数 add，签名已对照 tilelang/language/ascend_tile.py 验证；fp32 下正常行
sumexp>=1 加 1e-30 无影响，全 skip 行 0/1e-30=0），gqa.py 10 处 normalize 全部落地；
examples/gqa/eval_fix_verify/f4_causal_fullmask.py 6/6 PASS（含 mixed-block 场景需
额外对 running-max 做 `T.tile.max(m_i, m_i, 0.0)` 钳位以抵消加性 mask 的 max shift）。

**Proposed change**:
在归约/softmax 章节补充"全 mask 行语义"小节：normalize 除数加 tiny 常数（0/0→0）、
mixed-block 场景 running-max 钳位非负、以及 T.tile.add/T.tile.max 支持标量操作数的写法示例。
