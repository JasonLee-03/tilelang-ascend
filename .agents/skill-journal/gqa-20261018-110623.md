## Entry e1
- **target_skill**: tilelang-perf-optimization
- **target_artifact**: skill
- **target_section**: references/performance-antipatterns.md（sync / CV 掩盖类，新增条目）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
expert CV 流水 kernel 中 release-wait 可能兼任队列深度节流阀（pacing stall 是承重结构）：
把 ws 环从 2 槽加深到 4 槽后，释放侧等待如设计下降 ~6 成，但生产门等待爆炸、wall 反升
10.6–29.7%；把 C 步序 G2 前移后，攻击目标等待归零却整体转移到步首、wall 上升 9.6–24.0%。
"wall = busy + 往返残余" 的可加模型被证伪——往返停顿与有效 pipe 排空重叠，
"残余交接等待"不能默认当作可回收收益。

**Evidence**:
iter4 三方同会话交替 A/B（27/27 组额定频率）：C1(ns_flat=4) R3 60.55→66.94µs(+10.6%)/R2 +18.0%/R6 +29.7%；
C3(G2-first) R3 +24.0%/R2 +9.6%/R6 +10.8%。wait-id 遥测：C1 释放门 V-id3 −63%/C-id1 −61%/C-id5 −59%
但生产门 C-id2 +43.8µs/V-id0 +10.7/V-id4 +14.7，busy 不变（aiv_vec 35.7→36.5µs）；
C3 C-id1 33.7→2.3 但 C-id5 12.3→54.3、V-id3 20.4→21.4 纹丝不动（严格数据链同节拍重串行化）。
文件：`examples/gqa/perf_tuning/candidate_iter4_C1.json`、`candidate_iter4_C3.json`、
`msprof_op_iter4_*`（27 目录）、`perf_log.md` iter4 条目。

**Proposed change**:
在 performance-antipatterns.md sync 类新增条目："相位间等待 ≠ 可回收收益：release-wait 常为
承重节流（限制前跑深度、保持 MTE/FIX 队列浅与 ws L2 热集紧凑）。任何环深/步序/前跑深度的
结构改动，必须先做 per-semaphore wait-id 遥测区分空转等待与节流等待；判伪标准 = 改动后
生产门等待膨胀超过释放等待节省。"

## Entry e3
- **target_skill**: tilelang-custom-skill/tilelang-api-best-practices
- **target_artifact**: skill
- **target_section**: references/api-schedule-sync.md（flag / event 资源约束，与前轮 journal e4 的 cross-flag pending 深度条目同节互补）
- **type**: missing_constraint
- **severity**: high
- **status**: pending

**Observation**:
本地 SetFlag/WaitFlag event 不能当计数信号量叠 token 使用：iter5 首版对 Q 装载用本地 event
双 token 协议（两次 set 累积、两次 wait 消费），mc=2 冒烟即死锁（aicore timeout 507014，
launch 挂死）；重推导为单 token 形式（kv1 读作为唯一 free setter，MTE1 顺序排空隐含双读完成）
后全绿。前轮实证的 "cross-core flag 15 次上限 = pending 深度语义" **不可外推到本地 event**。

**Evidence**:
死锁现场与修复记录：`examples/gqa/perf_tuning/c2_design_iter5.md`（Q 本地协议重推导节）、
`candidate_iter5_C2.json`（framework_findings）、`candidate_iter5_gate0.log`；修复后 Gate 0
10/10 逐位一致（含 NaN/Inf 双 kv 块注入、mc=2 gate 边界），29+ 次上机零死锁。
未验证项如实标注：本地 event 的精确语义（binary vs 浅计数）未做隔离实验，
按 "深度 1 为唯一安全形" 记录。

**Proposed change**:
在 api-schedule-sync.md flag 资源约束处新增："本地 event（SetFlag/WaitFlag ISASI）按深度 1
单 token 设计，禁止多 token 叠加协议（真机实证死锁，症状 = aicore timeout 507014 launch 挂死）；
CrossCoreSetFlag 的计数/pending 深度语义不适用于本地 event。需表达多操作完成时用顺序队列
排空隐含或另占独立 id（注意 0–5 可用、6/7 保留的余量约束）。"
